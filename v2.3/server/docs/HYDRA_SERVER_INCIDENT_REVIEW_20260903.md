# Hydra Server 9 月 3 日故障复盘与生产维护说明

日期：2026-09-03  
范围：本说明只讨论本次 Server 故障、早盘依赖、上线流程和防御性编程；账户指纹另行讨论。

## 给团队的结论

今天早晨未能按时提交订单，不能简单归因于“防御性编程太多”。更准确的结论是：

1. 晚间的一次生产变更没有先完成与现有实例、数据库状态和启动流程的兼容性测试；
2. 原有的持仓归属检查把本应隔离的 paper 和 live 实例误判为冲突；
3. 这个检查发现问题后直接结束整个 Server，而不是只停掉有风险的自动调度；
4. systemd 又不断拉起 Server，形成 6,135 次重启；
5. 旧版 Windows 下单程序在早盘提交前还要访问 Server，因此 Server 故障被传导到了本来可以独立完成的 MiniQMT 下单环节。

所以，本次事故既包含未经完整测试就进入生产的流程问题，也包含我们原有代码中“检查范围过宽、失败范围过大、早盘耦合不合理”的设计问题。两者都要承认并修正。正确方向不是取消所有检查，而是让每项检查在正确的时间、正确的对象上生效，并且只隔离真正有问题的部分。

一句话概括：**安全检查应当像分路保险丝，哪里有问题就断哪里；不能把一个局部问题变成整栋楼断电。**

## 一、今天早晨为什么会依赖 Server

原来的设计意图并不坏：下单前再次确认“Server 上准备的订单”和“QMT 账户实际情况”一致，以免错误订单进入券商。

问题在于，这项在线核验被放在了次日 09:10 的下单关键路径上：

```text
旧流程
09:10 下单
  → 访问 Server、重新取单和对账
  → Server 正常才连接 MiniQMT
  → Server 不可用则整批不下
```

但订单在前一天晚上已经生成并拉到本地。到了早晨，真正必须实时确认的是本机 MiniQMT 中的账户、可用资金、可卖持仓、涨跌停价格和委托结果，而不是 Server 此刻是否在线。

因此，新的职责划分是：

```text
新流程
T 日晚间：Server 在线
  → 拉取订单
  → 本地独立复算并冻结订单批次
  → 完成 Server 账本与 QMT 的在线对账
  → 保存通过凭证

T+1 日 09:10：Server 可以离线
  → 校验本地冻结批次和昨晚的通过凭证
  → 读取 MiniQMT 最新账户、资金、持仓和价格
  → 提交订单
  → 本地持久记录提交状态，避免崩溃后重复下单
```

这不是删除完整性检查，而是把需要 Server 的检查提前到晚间，把券商侧实时检查保留在早晨。这样既保留安全性，也避免 Server 的临时故障阻止已经准备好的订单进入 MiniQMT。

## 二、连续宕机是怎样发生的

以下因果链由生产日志、systemd 记录和仓库代码共同确认：

### 1. 触发条件

根据团队现场记录，晚间变更直接进入了生产环境，但没有先完成与现有数据库和实例配置的完整回归。生产状态中，`paper_v53_v53` 与 `live_hydra_v481_rb` 都包含 `159915.SZ`。

两个不同账户或不同执行域持有同一只 ETF 本身可以是合法的。原有检查却只看到“两个实例出现相同代码”，没有正确区分 paper/live 和实际账户范围，因此将合法隔离误判成非法冲突。

### 2. Server 被整体退出

旧启动代码遇到 `OwnershipOverlap` 后执行 `SystemExit(1)`。这意味着出问题的虽然只是自动调度所依赖的一项归属配置，订单下载、成交回传、诊断和健康检查等 HTTP 能力也一起消失。

### 3. 自动重启放大故障

旧 systemd 配置会在失败约 5 秒后自动重启，而且没有有效的启动次数上限。日志确认：

- 第一次自动重启：2026-09-02 20:13:36（中国时间）；
- 2026-09-03 09:30 前累计计划重启 6,135 次；
- 每次启动都遇到同一冲突、退出，再被拉起。

自动重启适合偶发故障，不适合确定性的配置或代码错误。确定性错误不会被“再试一次”治好，只会制造重启风暴、放大日志并掩盖真正原因。

### 4. 故障传导到早盘下单

旧版 09:10 `submit` 仍会访问 Server 做订单和账本校验。因此，虽然订单已经在前一晚拉到本地，Server 不可用仍使程序在打开 MiniQMT 前终止。这是一次不必要的跨系统耦合。

### 5. 交易通路本身没有被证明失效

Server 恢复后，canary 委托已经成功成交。这说明 MiniQMT 的连接、提交和券商成交通路能够跑通。本次主要故障发生在 Server 启动和客户端编排边界，并不是 MiniQMT 交易接口本身失效。

## 三、当前 Server 上的“报告”是什么

生产机现在运行的提交是 `00016b9274ce1652d1d5bfa5f70e967fce0f1187`。这个版本新增了 `/dashboard/review`，名称是“Server 业务流程与风控闸门审阅”。

它的用途是：

- 把订单生成、领取、下单、成交、账本、影子策略和监控的边界放在一张清单里；
- 罗列已经存在的控制、待确认风险和需要团队决策的问题；
- 让团队对每一项留下评论和结论；
- 评论写入独立的评审表，不修改订单、成交、资金、持仓或策略状态。

它**不是**：

- 生产健康证明；
- “这些风险现在都已经发生”的报警单；
- 自动阻止部署或下单的新闸门；
- 对生产环境变量、QMT 在线状态和账户事实的替代验证。

页面自己也明确写明：它主要依据仓库代码、本地配置和审计材料，生产事实仍需现场补证。因此，应把它当作架构讨论目录，而不是把其中每个风险条目理解为当前故障。

截至 2026-09-03 12:47（中国时间）的只读核验结果：

- Server 提交：`00016b92`；
- systemd：`active`；
- 当前为单 worker；
- `/healthz`：正常；
- `/readyz`：`ready`，Parquet 和 ownership 均为 `ok`；
- 当前这次启动的 `NRestarts=0`。

这里的 `NRestarts=0` 只代表修复后这一次启动没有再次重启，不会抹掉事故期间日志中已经确认的 6,135 次重启。

生产工作树还有较多历史备份、候选文件和 macOS `._*` 文件。它们目前不是 Git 已跟踪源码的修改，不能据此认定正在影响运行；但它们会增加部署时选错文件、误判版本和误回滚的可能性，应逐步移出生产代码目录并登记归档。

## 四、生产 Server 应该怎样维护

先区分两个动作：

- **push 到 GitHub**：只是把代码放进远端仓库，便于审查和保留记录；一般不会自动改变生产机。
- **部署到生产 Server**：把某个版本拉到生产机并重启服务；这一步才会影响正在运行的系统。

真正不能做的是：把未审查、未测试的文件直接复制或拉到生产目录，然后立刻重启并让它接管业务。AI 写的代码也必须遵守同样流程；“AI 看过”不能代替测试证据。

### 最小上线流程

1. **在独立分支修改**：说明本次要解决什么、不解决什么、涉及哪些文件和配置。
2. **审查差异**：至少一名非作者确认代码、配置、数据库兼容性和回滚方案；不得把密钥写进仓库。
3. **先测试再部署**：运行完整自动测试，并针对事故场景做回归；策略实例、账户域、数据库迁移和 systemd 配置也属于测试范围。
4. **固定版本**：生产只部署一个明确的完整 commit SHA，不部署“某人电脑上最新的一份文件”。
5. **部署前留证和备份**：记录旧 SHA、服务状态和开关；备份数据库、私有配置与 service unit。备份放在生产工作树之外。
6. **受控部署**：同一时间只有一名操作人；停止、更新、迁移、启动各做一次，保存命令和结果。
7. **上线核验**：检查 commit、Git 状态、单 worker、`/healthz`、`/readyz`、日志、重启计数和实盘开关，再做小范围 canary。
8. **观察后交接**：至少观察一个完整关键窗口；把上线结果、异常和下一步写入 runbook。

### 关于回滚

代码可以回到已验证的旧 SHA，但已经发生订单、成交或结算后，不能简单用旧数据库覆盖当前数据库。否则可能丢失成交证据并在重跑时制造重复订单。实盘回滚的原则是：**代码可切换，交易证据只追加、不倒退；先保留现场，再决定如何恢复。**

紧急修复可以缩短流程，但不能没有流程：至少要有明确差异、另一人复核、备份、最小测试、固定 SHA 和事后补齐记录。

## 五、防御性编程是否过度

总体评价：**数量上不算明显过度，但原有实现中确实有两项严重的“放错位置”和一项“故障范围过大”。** 本次应精简和重构，而不是全面拆除。

### 必须保留

这些控制直接防止错账户、错数量、重复订单和账本污染：

- live/paper 执行域和账户范围隔离；
- 订单批次冻结、独立复算和完整性校验；
- 下单前检查最新 QMT 资金、可卖持仓、价格和整手数量；
- 同一订单的确定性标识、持久状态和重复提交保护；
- 不确定是否已提交时，先去 QMT 查找原委托，禁止盲目重发；
- 只有明确的 QMT 终态才能进入最终结算；
- 同一真实账户范围内的标的归属不得重叠；
- 真实成交和现金流必须留下不可随意覆盖的审计证据。

### 必须移动或缩小范围

- **Server 账本对账**：保留，但移到 T 日晚间；不能再成为 T+1 早盘提交对 Server 的在线依赖。
- **标的归属检查**：保留，但只在同一执行域、同一真实账户范围内判断冲突；paper 和 live、明确不同账户不应互相阻断。
- **启动检查**：发现归属风险时只隔离自动 scheduler，HTTP 的订单下载、回报和诊断能力继续可用，并把 readiness 标为 degraded。
- **进程恢复**：允许有限次数、带退避的重启；确定性错误达到上限后停止重试并报警。

### 可以在稳定后简化

- 初始化、canary、生成、交付等一次性上线开关，在完成首个完整实盘周期后可以合并成更清晰的阶段状态，减少操作人员面对多个布尔开关的困惑；
- 同一份数据、同一时点、同一来源的重复检查，如果不能覆盖新的故障模式，可以去重；
- 评审页面中的问题清单不应自动变成运行时闸门，只有被团队确认且有明确风险模型的项目才进入代码。

### 明确不应保留的旧行为

- 一个调度配置冲突让整个 HTTP Server 退出；
- Server 不在线就不允许已冻结订单进入 MiniQMT；
- 对确定性错误进行无限、快速的自动重启；
- 用“回滚整个数据库”处理已经接触实盘的故障；
- 把缺失的监控数据显示成正常的 0。

## 六、已经完成和仍待部署的修正

已经进入当前 Server 代码链并在生产生效的修正包括：

- ownership 按执行域和账户范围判断；
- ownership 异常只隔离 scheduler，不再结束整个 HTTP Server；
- readiness 能表达降级状态；
- systemd 改为单 worker、30 秒退避、5 分钟最多 5 次启动。

Windows live client 的新版本已经在 GitHub 分支 `codex/hydra-live-resilience-20260903`，最新提交为 `8f0bec3a82a1b39c22d6cb83ee0b77451026cd7a`。它实现了：

- 晚间 query + online preflight；
- 早盘 submit 零 Server 调用；
- 本地冻结批次和通过凭证；
- `SUBMITTING_UNKNOWN` 崩溃恢复和重复提交保护；
- 版本化 Windows 安装器、runner 和离线验收脚本。

这部分代码在 GitHub 上可见，但是否已经安装到实际 Windows/MiniQMT 机器，是另一件事，必须由机器上的安装路径、版本文件、任务计划和离线验收报告确认。**没有完成 Windows 部署前，不能仅凭 GitHub 已 push 就认为早盘解耦已经在运行。**

## 七、团队以后统一采用的判断标准

发生异常时先问四个问题：

1. 哪个组件出了问题？
2. 它最小应该阻断到哪里？
3. 是否存在已经冻结、可以独立继续的本地事实？
4. 继续或重试会不会制造重复订单、丢失成交证据或扩大故障？

只要坚持“变更先测试、生产只认固定 SHA、局部故障局部隔离、下单依赖尽量本地化、交易证据永不倒退”，Server 的安全性和可用性并不冲突。

## 可直接发到群里的短版

今天早上的问题不是简单的“防御性编程太多”。晚间变更进入生产后，旧版 ownership 检查把 paper 和 live 都持有 `159915.SZ` 误判成同一账户冲突；更严重的是，这个局部检查失败会让整个 Server 退出，systemd 随后重复拉起，日志确认累计重启 6,135 次。旧版早盘 submit 又必须访问 Server，因此 Server 故障被传到了本来已经在本地拿到订单的 MiniQMT 下单环节。

我们现在的修法不是删安全检查，而是调整边界：ownership 只在同一执行域和同一账户内检查；有问题只停自动调度，不让订单下载、回报和诊断接口一起消失；重启增加退避和次数上限；Server 对账挪到前一晚，第二天早盘只核验本地冻结订单和 MiniQMT 最新账户状态，不再访问 Server。

另外，push 到 GitHub 不等于部署。生产环境不能直接放入未测试文件后重启，正常流程至少应包含独立分支、同伴审查、自动和场景测试、固定 commit SHA、数据库/配置备份、健康检查、canary 和观察。当前 Server 已恢复并正常；新的 Windows 离线 submit 代码已经在 GitHub，但仍需在实际 MiniQMT 电脑上按版本化安装流程部署和验收后才算真正生效。
