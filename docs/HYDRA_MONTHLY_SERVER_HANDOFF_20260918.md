# Hydra 月度研究服务器化交接（2026-09-18）

## 这次上线解决什么

服务器原来已有订单、独立账本、成交归属、补差额与晚间执行计划能力，但没有定时运行 Hydra aa6b60d 研究源码的月度任务。这次补上“收到月末冻结数据 → 服务器计算权重 → 保存新目标计划”，不替换策略算法，不重做九月初交易。

研究源固定为 `aa6b60deef44b244764385e7b6bd681429b9b362`。部署分支为 `codex/hydra-monthly-server-20260918`，基于 Windows 热修复 `7bc302a4`（包含服务器 `ed1dffd`）。服务器与 Windows 是否已部署须看部署回执，不能根据分支存在推断。

## 谁做什么

1. **Windows 15:30 / 16:00 / 18:00 的 publish-execution**：继续上传当日原始执行价；月末当日额外从 MiniQMT 冻结完整 HFQ、原价、公司行动、跨月交易日历四份流，上传 `/hydra/research/snapshots`。只采集数据，不计算权重、不调整资金、不发委托。
2. **服务器独立 timer**：北京时间工作日 15:00—18:50 每十分钟检查收件箱；研究子进程最多十分钟、service 最多十二分钟、内存上限 2 GiB。失败退出并等待下一次，不拖垮 HTTP 服务。
3. **服务器研究结果**：一笔月度只保存一个执行计划，账户/策略/研究日绑定；重复上传与中途重启可以重试，已成功的计划不再复制。此步不写订单、不写资金或持仓。
4. **晚间 advance → query → preflight**：用已有独立账本、当时实际 QMT 账户事实、最新原始价格把计划转换为订单。若研究仍未完成，返回 `WAITING_EXECUTION_DATA`，不把旧目标当新目标。研究完成后重跑晚间流程即可。
5. **次日 09:10**：仍是本地冻结批次的离线 submit；本次没有重新加入服务器依赖。

50bp 上限、先卖后买现金检查、只用策略独立资金与收益、现有收盘结案/差额补单政策均不改。相邻自然日执行政策也不改：跨周末/长假时保留权重计划，等下一个合格交易对，用新参考价计算数量，不沿用月末旧价格。

## 今晚可上线 / 仍需实机验收

服务器可先部署新 API、收件表、独立研究代码与 timer。只有收到对应策略的月末冻结包才有工作，启用日期 `20260918` 排除九月初历史初始化。**Windows 未升级时，服务器不会凭空拥有四份月度数据。**

同伴应从同一分支安装器版本化部署客户端（沿用现有私有配置、Python、账本与任务配置），先运行安装器原生 PowerShell 解析校验；不要手工把文件混入旧 release。此轮开发环境没有 Windows/MiniQMT，不能把本地测试代替该验收。无需更换账号/API key，也不要打开初始化或 canary 闸门。

实机检查重点：

- 非月末 `publish-execution` 成功且 `monthly_research.status=NO_MONTHLY_RESEARCH_DUE`；现有 raw 上传不受影响。
- 首个月末 15:30：四份流成功冻结并收到 `RESEARCH_SNAPSHOT_STORED`；公司行动 None 与明确空表区分，查询无响应会报警，不伪装成没有分红。
- 服务器 `journalctl -u qmt-hydra-monthly.service` 出现 `MONTHLY_PLAN_READY`，月度表为 `PLANNED`；当时没有因此新增订单。
- 18:00 执行/拉取回执对应新计划，数量由独立策略净资产与最新执行价决定，仍最多 50bp。
- 安装器/任务的原生 Windows 验收未过，不修改现行 09:10 下单任务来绕过。

## 故障与恢复

- HTTP 回执丢失：重发同一冻结包；本地保留不可变包，不重新采行情。按账户/策略隔离缓存。
- 研究计算失败：现有 HTTP、结算、账本不受影响；新目标暂停发布。查独立 worker 日志，修复后重跑 worker。不会自动撤单或再下单。
- 月末数据完全没冻到：报 `WAITING_RESEARCH_UPLOAD`；禁止到下个月再取可能已受后续分红影响的 HFQ 历史冒充旧快照。交付同一天真实存档或单独审核补数方案。
- 18:00 才收到包：必须等 `MONTHLY_PLAN_READY` 后重跑 `query-preflight`。不存在“拉空也算当月完成”；不会自动补发早上的委托。
- 同一月份输入修订/另一期目标尚未执行：保留证据并提示审阅，不静默覆盖；不阻止无关策略、入金观察或正常结算。
- 代码回退：先停新 timer，回到上一个已核实 commit 并重启 HTTP；**不恢复旧数据库覆盖新的成交/资金事实**。新增表为增量兼容。若已有新目标/订单，先核实其生命周期再回退执行逻辑。
