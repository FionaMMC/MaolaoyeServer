# QMT 模拟盘与 Hydra 实盘：架构审计与渐进重构方案

审计日期：2026-09-06。性质：需求、代码、运行快照审计与设计建议，**不是部署批准，也不是实盘验收通过证明**。

后续详细设计见 [三盘共存：交易、资金与恢复架构规范](THREE_MODE_TRADING_ARCHITECTURE_SPEC_20260907.md)。本文保留当次证据；新文档补充三盘规则、资金分录与预留、26 项门禁、代码边界和迁移验收。

## 1. 结论先行

值得重构，但不建议推倒重写，更不建议先拆成一堆微服务。

系统的问题不是简单的“防御太多”或“代码太长”，而是：**同一件业务在不同链路中有不同含义；故障隔离范围不合理；本该自动恢复的步骤依赖人工补配置和对时间；部分真正需要严格保证的资金、状态、记账边界反而不完整。**

我建议保留策略算法和已经有效的保护，围绕以下四件事重新组织：

1. 一个交易业务核心：目标、订单、券商状态、成交归属、策略资金账本。
2. 两种券商执行环境：模拟账户与真实账户，共用协议和测试，但凭据、数据库和运行权限隔离。
3. 服务器计算与 HTTP 服务分进程；Windows 执行不依赖早上的服务器可用性。
4. 工作流按“前一步的持久结果”推进，而不只是赌几个定时任务恰好按时完成。

这不是为系统继续加层数，而是用清晰的状态和责任，替换已有的重复校验、特殊脚本与人工交接。

## 3. 三种“盘”必须先分清

| 名称 | 实际含义 | 当前实现 | 重构后定位 |
|---|---|---|---|
| QMT 模拟盘 | 订单确实进入券商模拟账户，有委托状态、拒单和延迟 | `v2.3/client` + 通用 pipeline | 与 live 共用交易协议，接模拟账户适配器 |
| Shadow 影子盘 | 服务器按价格和费用假设记虚拟成交，不接券商 | `ShadowLedgerService`、`shadow_*` 表 | 保留独立的模拟成交模型，复用估值和账务工具 |
| Hydra 实盘 | 研究冻结目标，经 server 生成订单，Windows MiniQMT 执行 | `hydra_relay` + `live_client` | 保留离线执行边界，补齐资金预留与状态恢复 |

不能用 shadow 成功证明券商通路成功，也不能用 mock 全部成交证明实盘部分成交、撤单、资金占用正确。

## 5. 具体发现：不是只看文件长度

### F01 — P1：重型计算阻塞 HTTP 事件循环，读取能力没有充分隔离

`app/api/admin.py:25` 的 async 路由直接调用同步 `pipeline.run()`；`hydra_relay.py:41`、`market_data.py:20` 等也在 async 路由内执行同步数据库/Parquet 操作。

本轮将 pipeline 替换成仅耗时 150ms 的无外部调用测试对象，同一事件循环中的另一个任务被延迟约 **153ms**。这是本地结构性复现，不是生产压测，也不是对历史宕机原因的直接证明。

建议：短期正确隔离阻塞 I/O；中期把策略和大数据作业交给独立 worker，API 接单后返回持久 job ID。不要只是增加 uvicorn workers，因为当前注释已经提示各 worker 可能重复启动调度，数据库也没有自动解决并发写问题。

FastAPI 对普通 `def` 和 `async def` 的线程池边界有明确说明；一个被直接调用的同步函数不会自动变成非阻塞。[FastAPI 官方说明](https://fastapi.tiangolo.com/async/)

### F02 — P1，多策略扩展前必须修：子账本有余额，却没有完整的执行中资金约束

证据：`live_client/core.py:161` 在校验时提前把 SELL 名义回款加入可用现金；`cli.py:203` 核对昨晚额度后，在 `cli.py:249` 循环提交，卖单被拒也继续后面的买单。没有等待卖出真实成交后再更新策略可支配现金。

本轮完全虚构的测试：策略现金 **0**，持有可卖 ETF 100 份，物理账户闲置现金 100,000；模拟 SELL 明确 REJECTED。实际代码仍继续调用 BUY，并记录 SUBMITTED。

这不证明生产已越权用钱，但证明“当前实现已经保证不借其他资金”说得太满，包括此前交接里的这一表述也需要纠正。

建议：冻结批次同时预留策略现金与可卖份额；执行器只使用“策略自己的已确认现金 + 已确认卖出净回款 − 已花费/已冻结金额”；再受物理账户可用资金约束。同一物理账户用一个提交协调器串行认领，不让多个独立进程各自以为那笔钱可用。

新增、撤回策略资本也要考虑已冻结额度；普通收益、股息、入出金记录不应因此全局停用。已发放的离线额度不能因网络超时就被服务器自动回收重发。

### F03 — P1：委托状态、成交增量、结案状态被压进同一个 status

四个具体表现：

1. `settlement.py:147` 的重复回报判断不包含 status。本轮先报 PARTIAL 100 份，再以同一成交数量/价格/时间报 CANCELLED，服务器跳过第二次，仍保存 PARTIAL。
2. `live_client/gateway.py:787` 逐笔读取时，一笔活动/缺失/未知订单就抛异常；`cli.py:335` 因而无法回传同批已经明确终局的其他订单。阻止补单合理，阻止接收已知事实不合理。
3. 旧 `client/trade_result.py:233` 在无成交且不是明确拒单时回退为 CANCELLED；通用 `pipeline.py:668` 会按日期把 PENDING 改 EXPIRED、PARTIAL 改 CANCELLED，而且该方法接受 execution_domain，并非天然只限纯 shadow。它不能作为实盘券商终态依据。
4. `live_client/gateway.py:155` 把“已部撤、已有成交”的券商终态映射为 PARTIAL；但 `hydra_relay.py:835` 又把全部 PARTIAL 当未决订单。即使券商已经明确结束，这条链也不能自然 close。这是客户端与服务器之间的契约冲突，不是多等几分钟能解决的。

建议拆清三件事：券商观察到什么、累计成交增加多少、该 attempt 是否可以关闭。允许不断记录活动状态与已知成交；只有尚有活动/不确定委托时不生成冲突补单。不因订单未成交就让其他信息全部丢失。

### F04 — P1：停止生成新订单，同时把日终收尾也关了

`hydra_relay.py:408` 的 `close_attempt()` 调用 `_gate_live()`；后者要求 `live_enabled=true` 且生成订单风控配置就绪。

本轮创建已终局的虚构 live attempt，随后关闭生成开关，调用 close，复现“Hydra live 订单生成闸门关闭”。服务器私有配置文件及运行中进程环境均读取到 `QMT_LIVE_ORDER_GENERATION_ENABLED=false`。这解释了一处现存能力限制，但本轮没有调用写接口，不能据此断言此前每次未结案都由该开关造成；更不能擅自打开。

建议：把“增加交易风险”的权限与“收回报、撤单、对账、结案”的权限分开。停开新单必须仍能收尾。此问题属于我们现有实现的错误耦合，不应归咎于使用者不会操作。

### F05 — P1：补单已创建但响应丢失，重试不能取回原结果

`hydra_relay.py:330` 先检查不存在未决订单、前一个 attempt 为 RESIDUAL，然后创建新 attempt；没有先按请求标识找到已成功的相同请求。

本轮模拟前一批全部取消、close 成 RESIDUAL，第一次 retry 生成 2 笔订单；原请求再次发送得到“前一 attempt 尚有未决订单”。这避免了简单重复生成，却把“服务器成功、本地没有收到回执”的正常恢复变成人工事件。

另一个窗口：`cli.py:486` 每次 close 重取快照并计算新 evidence；server `hydra_relay.py:421` 对已结案要求原 evidence。若响应丢失后现金/市值变化，新快照可能使恢复再次被拒。

建议：本地先持久化请求与请求 ID，再发送；服务器保存请求结果并允许同请求取回，内容不同才冲突。这也使重试逻辑更短。[AWS：幂等请求与安全重试](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)

### F06 — P1：账务事实、估算费用和收益展示尚未闭环

证据与影响：

- `settlement.py:192` 使用估算佣金；execution quality 也叫 `estimated_fees`。没有找到完整的券商交割费用入账及差额更正流程。
- `settlement.py:352` 缺少归属映射时只 warning 并跳过账本更新；现金不足时会记录成交但跳过某个子账本更新。需要一个明确、可恢复的“成交已收到、归属待处理”状态，而不是靠读日志发现。
- `perf.py:107` 直接用 NAV 变化算收益率，未关联 cash-flow。虚构例子：资产从 1,000 变 1,100、增加的 100 全为入金，当前公式报告 +10%，而投资收益应为 0。
- `perf.py:71` 缺估值价格时把该持仓市值按 0 处理。应标记估值不完整，保留可解释的价格来源和时点，不能发布成正常完整 NAV。
- live close/retry 未调用普通 `PerfService.snapshot_all`；本轮服务器 `perf_snapshots` 没有 live 行，不能把“有执行质量记录”当成“有实盘净值闭环”。

建议：账务使用可审计的分录/事件及余额投影；现金精确到最小货币单位或定点数，明确舍入。费用先 provisional，再用正式回单更正。资本划拨与策略投资收益分开，日报给出资产、净入资、收益及未解释差额。资金充足性检查不等于会计对账。

### F07 — P1/P2：通用模拟盘仍是“清旧批次再重算”，导致补丁式保护越叠越多

`pipeline.py:262` 清旧订单，之后分别提交策略状态、raw signals、归集订单和 NAV；`aggregate.py:88` 每次生成新随机 order ID。任一阶段失败可能留下不同步的中间状态。

因此才需要 already_fetched、already_settled、force、孤儿成交修复等历史补丁。`pipeline.py:237` 任一 strict instance 被挡还会直接返回，阻止整个域的本次 pipeline。

建议：先构建新的不可变批次，验证后原子发布；旧批次保留，不靠删除实现幂等。每个策略实例独立记录运行成功/失败，只有真实共享资金约束才上升到账户级协调。跨策略有真实依赖时明确记录，不能一律放行或一律全停。

### F08 — P2：定时任务负责了太多业务判断，缺少持久工作流

服务器存在 systemd timers（研究刷新、行情 fallback、影子账本等）；API 内又有可启用的 APScheduler；Windows 又有多个工作日任务。

新代码时序是 14:55 cancel → 16:05 close → 16:20 retry → 18:00 query/preflight。但 close 超时后再等 5 分钟重启，可能与 16:20 retry 重叠；错过一次任务也不会自然补齐流程。`Invoke-HydraLiveOperations.ps1:65` 等用输出正则判断阶段结果。

建议：时间只负责唤醒，状态决定继续哪一步；使用结构化 JSON 结果、明确退出码、可查询的 job 状态。区分 `NO_CHANGE`、`WAITING_DATA`、`WAITING_BROKER`、`FAILED`，不要把“没单”统称成功，也不要把“等终态”统称崩溃。Windows 保留券商时间窗口调度，服务器保留业务作业调度，各自只有一个权威。

所有市场时间显式用 Asia/Shanghai。撤单截止属于券商/交易方式政策，不应散落在 CLI、PS1 和历史文档里。当前 14:55/14:57 配置不能被解释成适用于所有品种的统一交易所规则。

### F09 — P2：数据仓与审批信息同时承担配置职责，日常运维成本过高

Hydra 的不可变四流数据是优点；但 retry raw hash、target ID、rebalance ID 仍要填进私有 env。下一周期变化的是业务产物，不是机器配置。

`stage_retry` 仅要求 raw 的 as-of 早于 trade_date，未在该方法验证下一有效交易日、更新后的停牌状态以及最大允许陈旧程度。Windows 再使用另一份实时 QMT 日历算日期。正确性依赖外部人工把信息对齐。

通用 Parquet `append` 是 read/merge/write 原文件，重复日期先到先得；没有显式数据修订版本或原子发布。它与 Hydra 内容寻址仓是两套语义。

建议：同一数据注册表管理 source、adjustment、as-of、coverage、revision；数据纠错新增版本，任务绑定版本。策略数据清洗要求属于策略契约，不用全市场一刀切。已批准目标和补单定价政策由 server 自动携带给客户端，日常不再手填三份 ID/hash。

### F10 — P2：发布和文档存在双重事实来源，包括安装器自身也需简化

- 代码、研究产物、DB、私有配置、备份和候选文件混在工作目录。仓库跟踪 11,782 个 Parquet；本地 `.git` 约 62MiB、`v2.3/data` 约 94MiB。这是发布管理问题，不能直接推导为运行内存瓶颈。
- 活跃代码约 27,337 行（粗计 Python/PS1/BAT，排除 tests/vendor/data）；dashboard 的 1,936 行中含内嵌页面，不应当成 1,936 行交易核心。
- `CLAUDE.md` 仍写“规划阶段”，旧需求文档仍写不主动撤单、老资金上限或旧任务时间。后加的 handoff 相互覆盖，使用者需要读历史才能判断当前规则。
- `Install-HydraLiveClient.ps1:290` 先切 pointer/runner 再复制其他脚本，复制失败发生在后面的回退 try 之外；有局部切换风险。
- `Register-HydraLiveOperationsTasks.ps1:52` 会 `-Force` 覆盖同名新任务；失败处理没有完整恢复被覆盖的共享任务定义。这不是完整事务式发布。

## 6. “是不是防御过度”的明确评价

**有过度耦合和错误的保护位置；不是所有保护都多余，也不是现有保护已经足够。**

| 处理 | 具体例子 |
|---|---|
| 保留 | 真/模拟账户隔离、策略资本额度、数量与价格边界、幂等提交、未知委托不盲目重发、冻结批次不可静默替换 |
| 移到晚间 | server 可用性检查、目标来源验证、完整账本核对、数据完整性检查 |
| 保留在执行现场 | 券商账户身份、实时可用现金/可卖份额、自己的额度占用、合法执行窗口、不确定提交恢复 |
| 缩小影响范围 | 一笔未知订单影响它自身及冲突补单，不影响上传其他明确成交；一个策略缺数据不让整个 HTTP 服务退出 |
| 删除或改成可恢复状态 | 响应丢失后无法重取结果；close 被生成开关挡住；已确认未发单却被当成可能发单；每日人工填 target/retry hash |
| 降级为质量提示 | 日报、IOPV 缺测、企微失败；不据此删除已发生的委托事实。若某项指标是业务明确批准的交易前置条件，则执行该政策，而不是一概降级 |

当前 submit 在取得行情前就先标记 SUBMITTING_UNKNOWN（`cli.py:285` → `gateway.py:674`）。因此行情缺失也可能留下“可能已经下单”的标记；可以把前置读取放到提交认领前，将真正的不确定区间收缩到券商写调用附近，同时保留先记意图再调用的原则。

传输政策：保留用户已批准的 HTTP 决定，不趁重构增加 HTTPS 上线门槛。但本地 hash 只证明内容一致性，不等于网络来源真实性；HTTP 上同时替换内容和 hash 的风险不会凭这些检查消失。未来传输认证可以独立改进，不应混为这次宕机/调度问题的解释。

## 7. 建议目标架构：模块化单体，少量明确的进程边界

### 7.1 责任划分

| 组件 | 应当负责 | 不应当负责 |
|---|---|---|
| Data / Research Worker，服务器 | 采集任务结果登记、清洗、冻结数据、运行策略、产出目标 | 在 HTTP 请求内长时间计算；直接向真实券商下单 |
| Trading Core，服务器 | 目标转订单、额度预留、批次发布、回报入账、差额补单、账务 | 控制本地桌面会话；将“时间到了”当券商已撤 |
| API / Dashboard，服务器 | 快速接受请求、返回 job/批次/账本状态，展示诊断 | 绑定策略计算进程生死；修改交易事实来修显示 |
| Execution Agent，Windows | 冻结执行包、本地额度占用、连接 QMT、提交/撤单、采集并可靠回传 | 重新计算策略权重、补单数量和服务器限价；早上下单前等待 server |
| Reporting Worker，可先与业务 worker 共部署 | 收盘估值、净值、分红费用差异、执行质量 | 报表失败导致委托/成交回滚 |

先保留一个仓库、共享领域代码。服务器先两个主要进程：API 与 worker；Windows 一套执行内核，paper/live 分别运行在隔离环境。Dashboard 可以先只抽成静态资源，不必另建复杂前端工程。

### 7.2 核心数据对象

保留已有 target → rebalance → attempt 思路，逐渐泛化名字，而不是再并列新增第三套 Hydra 特例：

- `StrategyInstance`：算法版本、运行域、生命周期（active/retired）、资金账本、策略交易政策。
- `Account`：物理券商账户；明确 `account_id` 与 `strategy_id` 是不同对象。
- `DataSnapshot / Target`：数据版本、决策时点、目标与来源。复权/原价明确区分。
- `ExecutionBatch / OrderIntent`：固定批次与订单标识，发布后不可原地改写。
- `CapitalReservation`：本批次占用哪一个策略的现金/份额；不是复制物理账户余额。
- `BrokerObservation / Fill`：券商状态和成交事实分别记录；收不到就是未知，不伪装取消。
- `LedgerEntry`：成交、费用、股息、份额变化、划拨及更正；余额是这些记录的投影。
- `Job / RequestReceipt / Outbox`：可恢复的作业进度、请求结果和待发送消息。

不要求为了这些对象再搭 Kafka 或全量 event sourcing 平台。先用现有数据库中的少量明确表、约束和事务即可。

### 7.3 正常的一天应该怎样运行

1. 服务器拿到所需数据，运行策略；无需调仓时明确记录 NO_CHANGE。
2. 需要交易时生成并发布一个批次，预留策略额度。
3. 晚间 Windows 下载执行包，核对目标/账户/额度/当前账本，冻结并生成次日任务。
4. 次日执行器不请求服务器；按自己的额度及券商真实可用量提交。卖出未成交时，不提前使用这笔回款。
5. 提交、活动状态、成交和撤单观察先落本地；服务器断开也不丢记录，恢复后重传。
6. 到合法撤单窗口，对本批次仍活动的委托发撤单请求；等待真实终态。
7. server 接收事实并入账；全部相关委托明确终局后 close，残差由 server 决定是否生成下一次 attempt。
8. 估值、收益、费用/股息核对独立完成；展示“完成/等待/异常及下一步”，不要求同事翻多个脚本。

其中人工只处理真正需要决策的事件：改策略、增减资本、改变交易政策、无法唯一确认的委托、解释不清的账务差异。正常每日运行不应再人工审批相同的技术字段。

### 7.4 数据库选择

不能因看到 SQLite 就直接认定需要 PostgreSQL。目前规模不构成立即换库的证据。

先完成短事务、唯一约束、写入协调、明确迁移版本、可靠备份，测量锁等待/队列时延。WAL 可以改善读写并发，但仍不是多写者并行方案，也不能解决重复记账或错误状态机。若后续多账户并发任务确实超出这一安排，再迁 PostgreSQL。[SQLite WAL](https://www.sqlite.org/wal.html)、[事务隔离说明](https://www.sqlite.org/isolation.html)

不得只改一个 DB URL 就宣称完成换库：当前迁移包含 SQLite PRAGMA/SQL，现金和订单并发约束也需逐项验证。

优先次序：F02 资金约束 → F03 状态/回报 → F04 收尾权限 → F05 请求恢复；同时处理 F01 的 API 阻塞隔离。

### 第 2 阶段：统一协议与执行内核

- 为模拟盘和 live 定义同一个有版本号的批次/回报协议，保留独立运行实例。

出口：同一份回归场景在 mock 与 QMT 模拟账户得到相同状态语义；券商行为差异由适配器处理。

### 第 3 阶段：独立 worker 与持久工作流

- API 只登记命令；任务持久化并按依赖恢复。
- 统一研究数据完成通知、价格版本与交易日历；server 自动选择获批目标/补单数据。
- 重跑同一策略同一版本得到同一批次身份；失败不清掉上一份已发布订单。

出口：停掉研究计算进程，API 仍可读批次和收回报；停掉 API，已冻结的本地下单照常；错过一个唤醒，允许在合法窗口内从检查点恢复。

### 第 4 阶段：账务与绩效完整化

- 物理账户、策略子账本与未分配储备分别建账；成交归属可重建。
- 正式费用、支付日股息、拆并份额、更正记录接通。
- 日终 NAV 与入出资剥离，明确 provisional/final 和估值缺失。
- 多策略同标的、同时买卖、入出资及离线额度占用联合验收。

出口：每个策略“本金 + 净划拨 + 投资盈亏”能解释当前净资产；合计与物理账户/未分配储备对得上。

### 第 5 阶段：影子对比、灰度与旧路径退役

- 新系统先只读影子运行，不接第二个有写权限的执行器。
- 固定同一数据/算法/资金快照，对比目标、数量、价格、费用及账本。
- 在专用模拟账户跑异常场景，随后再按明确批准做实盘灰度。
- 经验证后退役通用 live trigger、旧执行脚本和冲突文档入口；只归档历史，不批量删除证据。

回退原则：回退兼容的代码/任务版本，保留已经发生的订单、成交和资金分录。不能把旧数据库恢复到成交之前然后重新发同一批订单。

## 10. 接下来最值得做的一件事

**先做一个“小而完整的交易闭环内核”整改，不先搬目录，也不先美化 Dashboard。**

第一批工作的验收句子应该是：

> 无论服务器暂时不可用、部分订单未成交、卖出失败或回报重传，每笔委托都有确定归属；每个策略只动自己的可用资金；已经发生的成交不丢、不重记；系统能明确告诉操作者停在哪一步，以及是否会自动恢复。

以此为基座，再把旧模拟盘和后续实盘策略逐个接入。目标不是“严谨且永远不失败”，而是**失败范围小、事实不丢、恢复路径明确、日常操作简单**。
