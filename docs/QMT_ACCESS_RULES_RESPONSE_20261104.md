# QMT 外接收紧：影响与应对方案

日期：2026-11-04。起因是平安量盈 QMT 的升级通知：**11/06 17:00–20:00** 升级，内置 Python 将不能读写本地文件、不能联网，并按规则关闭独立交易功能。本文整理了网上能查到的规则和各券商的执行情况，评估对我们的影响，提出应对方案。生产库只做了只读查询，没有改动服务器、客户端、任务或配置。

平安的通知原文网上没有找到，升级时间来自本地的《量盈QMT新版模拟客户端探索报告》（11/03 升级前测试）。其余内容和下文几家券商的通知一致。

## 一 结论

1. 我们的 Windows 客户端是外部 venv 里的 Python，通过 xtquant 的 `XtQuantTrader` 连接 `userdata_mini` 下单（`v2.3/live_client/gateway.py:470`），也就是"独立交易"模式。这个模式取消后，**从 11/09 起不能再自动下单**。
2. 新规下，个人账户没有合规的外接途径。能继续自动交易的只有一种：交易信号完全在 QMT 内部产生的内置策略。
3. 建议：
   - **近期**（11/06 起，包括 11/30 月末）改成"服务器算目标、人工下单、上传成交"。
   - **中期**评估把 Hydra 整个搬进 QMT 内置策略；V713 继续人工执行。
   - **不要**使用任何"解除限制"的桥接或自动化手段。

## 二 外部情况

### 规则

2026-08-28，中证协和中基协联合发布《证券公司交易信息系统接入管理规范（试行）》，当天生效，2015 年的外部接入评估认证规范同时废止。

- 系统接入指券商提供接口等技术手段，与投资者的订单生成系统交互，并接收、处理其订单。
- 规范列出的接入客户都是机构：券商及子公司、公募、期货资管子公司、银行理财、保险资管、私募管理人、合格境外投资者，以及协会认定的其他投资者。**个人不在其中。**
- 私募管理人的条件：在基金业协会登记、首只产品备案满一年、合规风控和交易人员独立、至少两名系统接入技术人员。
- 一位国投证券客户经理转述："文件交互接入仅能提供给满足规定要求的金融机构及私募管理人"，个人客户的文件单交易将被关闭。

### 券商执行（第三方转述，非官方原文）

| 券商 | 时间 | 内容 |
|---|---|---|
| 未具名 | 9/24 通知 | 9/30 收市后关闭所有 mini QMT 权限；内置 Python 拦截 `open/read/write`，阻断 HTTP/TCP/UDP，禁止连接局域网和本机数据库（MySQL/Redis/SQLite），涉及上述功能的第三方库同样被拦截；"文件单"模式停用 |
| 未具名 | 10/08 通知"内置Python策略功能调整" | 10/23 完成升级；取消登录页的独立交易选项 |
| 江海证券 | 10/23 收盘后升级，10/26 启用新版，旧版不可用 | 取消独立交易选项；确认不再支持 xtquant，只能用 QMT 内置策略 |
| 平安证券 | 11/06 17:00–20:00 | 内置 Python 限制文件读写和外部网络，按规则关闭独立交易（据本地探索报告） |

各家通知都明确不受影响的只有一种情形："采用内置 Python、且交易信号完全在 QMT 系统内部产生、不与外部环境进行任何交互的策略模式"。

## 三 对我们的影响

### 客户端

- 9 个 `Hydra-Oms-*` 任务（`Register-HydraOmsTasks.ps1:37-47`）的委托、撤单、查询和快照都依赖 `XtQuantTrader`，升级后全部无法工作。
- 外部 `xtdata`（只取行情、不下单）在新版下是否还能连上，需要升级后实测。如果不能用，Hydra 月度包（`monthly_publication.py`）也会断。
- 限制针对的是 QMT 内置 Python。同一台 Windows 机器上，QMT 之外的普通程序照常可以联网。

### 服务器

- 11/09 起收不到收盘快照。依赖快照的对账、实盘绩效（`qmt-live-performance`）、V713 估值和合成账本都会缺数据。每个任务缺数据时是报错还是静默跳过，**待核实**。
- 日线行情已有服务器侧的 Tushare 兜底（`qmt-market-fallback`，17:05），不依赖客户端。
- `ingest_snapshot` 发现快照与账本不一致时，会把活跃周期置为 `HELD`（`app/oms/cycles.py:314`）。人工交易产生的成交没有 OMS 委托号，直接按现在的方式上传会被判为不一致，所以人工执行需要单独的录入方式。
- [10 月末问题记录](https://github.com/FionaMMC/MaolaoyeServer/pull/7)的第 3 条（Hydra 月度包无人生产）方向要变：不应再补客户端上传，数据来源应改到服务器侧，前提是先核对和研究数据是否一致。

## 四 可选路线

| 路线 | 做法 | 合规 | 开发量 | 主要代价 |
|---|---|---|---|---|
| 1 服务器算、人工下 | 服务器照常生成目标和订单清单；操作员在 QMT 界面下单；收盘后上传客户端导出的持仓和成交 | 风险最低：人工下单不是系统接入 | 小：OMS 加人工执行模式，加导出表的转换和上传 | 调仓日人力；没有分批卖买和价格带控制，执行质量下降 |
| 2 策略搬进 QMT 内置 | 用 QMT 自带数据在内置策略里计算信号并下单 | 符合通知里的豁免条件 | 大：重写，并逐项验证数据 | Python 3.6 或 3.12 环境；状态只能存在 QMT 内；没有通知；服务器只能靠人工导出拿到成交 |
| 3 合格机构接入 | 资金放进满足条件的私募产品，申请正式接入 | 合规 | 中 | 只在团队已有合格管理人和产品时可行 |

Hydra 的输入只有 ETF 行情和分红，路线 2 的数据基本可以靠 QMT 自带数据解决。V713 用到 ROE 和股本的时点数据，用 QMT 财务数据重建后，需要证明与研究结果一致，工作量和风险都大得多。

两个实例的持仓标的不重叠（Hydra 是 ETF，股票腿是个股）。所以无论走哪条路线，人工成交都可以按标的归属到对应实例。

## 五 建议步骤

### 11/06 升级前（每一步都需要批准）

1. 确定 C3 的处理方式：
   - 方案一：11/06 收盘后在服务器上关闭 C3，未完成部分人工补齐。
   - 方案二：11/09、11/10 两天直接人工执行。
2. 11/06 的 EOD 和 18:00 上传完成后，停用 Windows 上的 9 个 `Hydra-Oms-*` 任务。
3. 把服务器切到不自动执行的状态，避免继续生成没人消费的计划，或者报一串误报的告警。
4. 升级后用新版客户端实测一次：外部 `xtdata` 是否可用，客户端能否导出持仓和成交表、导出的格式是什么。

### 11/30 月末前（路线 1）

1. OMS 增加人工执行模式：
   - 生成可打印、可导入的订单清单。
   - 接收导出的持仓和成交表，按标的归属到实例，再对账。
2. 和[月末问题](https://github.com/FionaMMC/MaolaoyeServer/pull/7)一起统一修订：
   - 月份判断。
   - 2027 年日历。
   - Hydra 月度包改由服务器取数据。
3. 11/27 前在库副本上用真实月末数据跑通：数据 → 目标 → 订单清单 → 导入成交 → 对账。

### 中期（路线 2，只考虑 Hydra）

在平安书面确认之后再启动。先用模拟客户端验证：
- 数据：ETF 行情和分红与研究数据一致。
- 交易：模拟报单、查询、撤单可用。
- 状态：重启后状态能保持。

再决定是否迁移。

## 六 不建议的做法

- **第三方"解除限制"的桥接、纯协议接口，或者用模拟键鼠驱动客户端。** 这些在实质上就是外部系统接入，有账户被限制的风险。
- **每天把服务器算好的订单 JSON 粘贴进策略代码。** 探索报告证明它技术上可行，但信号不是在 QMT 内部产生的，不符合豁免条件。江海那个项目也判定外部注入参数不被允许。没有平安的书面答复，不要依赖这种做法。
- **不升级客户端。** 江海的旧版在升级后不可用，不应假设平安会不同。

## 七 需要向平安确认（最好要书面答复）

1. 通知全文，以及"按规则关闭独立交易"具体适用于哪些账户。
2. 我们的账户类型，以及是否有任何合规的接入途径。
3. 升级后，在客户端界面手动导入篮子订单（组合交易）是否允许。
4. 人工往内置策略填写目标权重或参数，算不算"外部交互"。
5. 外部 `xtdata`（只取行情、不下单）是否保留。
6. 客户端能否导出持仓、委托、成交，导出格式是什么。
7. 账户的程序化交易报告是否已经完成。走路线 2 时，内置策略仍属于程序化交易。

## 八 其他观察

11/03 股票腿有 36 笔买单被券商受理后又被拒，全部是 300、301、688 开头的标的。同一批板块也有成交，所以不像是权限问题。原因还没有查。
