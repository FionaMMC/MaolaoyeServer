## 次日买单被标记 SUSPENDED 的判断

服务器错误链路在当前代码中仍存在：`cycles.py:226` 从当晚快照的 `is_trading` 建名单，交给次日买入计划；`planner.py:186` 把不在名单中的缺口标为 `SUSPENDED`。这不足以证明次日真实停牌。

本次用同一组临时账本和合成行情做对照：

| 输入差异 | 对账 | 次日计划 |
|---|---|---|
| 收盘快照 `is_trading=True` | 通过 | 生成买单，资金不足部分单独记为 CASH |
| 仅将上述状态改成 `False` | 通过 | 买单为空，缺口全部记为 SUSPENDED |

这复现了错误机制，但不是对报告中三笔真实订单后续状态的复查。

修复边界建议：

- 次日计划按冻结目标、已确认持仓、策略资金、限价和执行窗口生成；不把前日即时状态当成次日停牌证明。
- 客户端保留真实观测，不把状态强行改为 True；本次不新增客户端停牌拦截。真实拒单及原因按券商事实进入原有状态机与余量流程。
- EOD 收盘价采集与盘中买卖盘口要求分离。当前 `market_quote` 要求买一、卖一有效，盘口清空时可能把仍有有效价格的证券整个漏掉；收盘锚还需核对交易日、来源和时间。
- 保留现有资金/数量上限、防重复、日终到期、部分成交和窗口终局。不另造一套 16:00 补单流程。
- 修复代码不会自动改写已经缓存或已生成的计划。先核对事故周期的实际终局；仅在仍有有效未执行责任时，生成有版本、有差异清单的恢复方案，同步服务器和 Windows 缓存，不能重放过期订单。

客户端存在版本差异：报告写的是 `tick.openInt` 的状态集合判断，本地 `gateway.py:584` 却是 `detail.IsTrading`。因此不能按报告行号直接打包替换。迅投官方资料也分别列出证券状态、合约是否可交易和行情字段；应根据现场 QMT 版本与原始字段样例建立映射，不能仅凭一个布尔值推断跨日状态。[XtData 官方字段说明](https://dict.thinktrader.net/nativeApi/xtdata.html)

## 与共享账户直接相关的阻塞

1. **账户级周期和策略级周期尚未分开。** 当前每个 account alias 只能有一个活动周期，人工操作要求账户下恰好一个 live 实例。增加 V713 后，正常的两个策略周期和人工归属会发生冲突。
2. **客户端拿全账户持仓判断单策略目标。** 若 Hydra 已持有某 ETF，V713 的买入缺口可能被错误抵扣；卖出也必须受 V713 自己拥有的份额限制。物理可卖量只是另一层上限。
3. **账户资源没有完整的跨策略预留。** 两个计划、人工单和提交结果 UNKNOWN 的订单必须共同占用真实现金和可卖数量。当前自动 OMS 仅在 SUBMITTED 后扣减本次循环现金，UNKNOWN 没有同等预留。
4. **动态股票池不能照搬固定九只 ETF。** 新目标、旧持仓、未结订单及企业行动责任必须共同进入管理名单；旧股卖净、订单终结和相关责任结清后才能退出。
5. **“可共享证券的账本”不等于“能共享执行账户”。** 现有 attributed 归属可复用，但还需要统一调度、资金预留、可卖量约束、人工操作归属与账户级总量对账。

首版建议保留两个策略的独立订单和成交归属，通过同一账户执行器协调。不要顺手引入策略间内部净额交易；那会改变成交归因、交易成本及策略比较口径，需要另行设计。

## 关键设计要求和验收细节

### T03 至 T06 目标与股票交易

V713 的 `decision_date` 是目标执行的下一交易日，`as_of_date` 是已完成月末；OMS 又要求执行日晚于 `signal_date`。字段直接照搬会错过原定首日，遇到周末或长假还可能推迟更多。适配器必须明确数据观察日、目标生成日、首次可执行日，按现有 V713 意图做测试。

当前纯计划器固定 `LOT=100`、`TICK=.001` 和 Hydra 专属价带。本次合成输入 `10.23`、买价带 50bp 产生 `10.281`；若该证券最小档位为 0.01，这个结果就不合法。规格应来自带版本的证券资料，客户端在实际提交前再次验证当日约束。QMT 官方提供 `PriceTick`、涨跌停价、可用持仓等字段，适合用于该契约，但具体支持板块和申报规则仍需按券商及交易所核验。[行情资料](https://dict.thinktrader.net/nativeApi/xtdata.html)、[交易与持仓资料](https://dict.thinktrader.net/nativeApi/xttrader.html)

旧 V713 的篮子要求出现的权重为正，新执行适配器则必须额外表示退出证券的零目标。这是执行目标的扩展，不能修改研究篮子的原哈希或把零权重塞回原输入后冒称源文件未变。

`OmsCycle.policy` 虽然已保存，后续计划仍调用运行时 `self.policy`；在同时支持 Hydra/V713 前，需要按周期恢复冻结规则、证券规格和费用版本。

### T08 至 T11 共账户与账本

共享账户应同时满足：

- 可下单现金不超过该策略未占用现金，也不超过物理账户未占用可用现金；不能重复减已经体现在券商可用现金里的冻结量。
- 卖出量不超过该策略拥有且未预留的可卖份额，也不超过券商的物理可卖量；策略可卖份额按该策略的成交日期和证券规则计算。首版不借用另一策略的昨仓额度来使本策略当日新买的 T+1 股票提前可卖。
- V713 的目标缺口用 V713 子账本持仓计算；物理账户总持仓仅用于总体约束和对账。
- 券商一笔成交由订单身份明确归属一个策略；累计成交、重复回报、迟到成交和费用更正不能跨策略。
- 同一证券可由两个 attributed 策略共同持有；归属清单和账户对账不得将另一个策略的持仓误当外部或无主资产。
- 账户总量对账应覆盖策略账本、未分配资金及有证据的外部资产；不能把不明差额自动分给某个策略来强行配平。

期初 V713 资金数额、是否从 Hydra 正式划拨、是否认领已有真实持仓需要在 T11 形成具体可审批清单。这里未假定金额，也未授权自动转移任何资金。

### T02、T07、T13 提交与恢复

当前客户端 `main` 仅在 `sell/buy` 调用配置提交开关；人工单的 `intraday` 路径可直接进入提交函数。服务器人工 pending 也没有使用自动计划的同一 enable 判定。应把所有新委托汇入同一硬性校验点，同时保留事实采集和风险降低操作。

`oms-agent.db` 目前是配置状态库旁的固定文件名，计划查询只按交易日和阶段取最后一条。共账户两策略必须改为带完整身份的缓存和查询；仅复制 env 文件或新建任务名不足以隔离。

现有安装验收主要覆盖旧 core；实际 OMS 日志库也不是安装脚本默认备份的那一个。应把真正使用的 journal、SQLite 一致性副本、spool、HOLD、发布包和任务清单纳入恢复演练。回滚保留已产生订单和成交，先停止新单、核实未决责任，不用旧数据库覆盖真实交易，也不重新启用不认识 OMS 订单的旧程序。

委托备注已有简短确定性订单号可复用，但恢复不能仅见相同 remark 就认领；要再核验账户、方向、证券、数量和价格。极简 QMT 对备注长度有限制，新增策略身份应在该约束内设计并实测回读。[QMT 官方备注说明](https://dict.thinktrader.net/nativeApi/question_function.html)

### T12 净值与公司行动

已有通用行情推送使用前复权，实盘估值服务读取 close 却未验证复权元数据。这证明存在数据通路风险，不证明当前生产 V713 文件已经错误。需要为执行锚和 NAV 建立明确的未复权输入与覆盖校验；研究复权价格另存契约。

首版公司行动最低要求是：现金分红正确记录登记日权益、应收与实际到账；税差/分次到账/送转等有带证据的处理单、复核、更正和幂等机制。无法自动处理时暂停相关交易、继续保留券商事实并显示差异，不能静默丢弃，也不能以旧持仓覆盖券商新数量。全面自动化可另排后续工作。

## 端到端验收矩阵

| 场景 | 必须观察到的结果 |
|---|---|
| 收盘全部 is_trading=False、盘口为空 | 有可靠收盘锚时次日目标仍被规划；状态/缺价原因明确，不冒充停牌 |
| 目标内真实停牌、涨跌停、权限拒绝 | 事实与拒单原因可追溯；不无限重试；不突破冻结窗口/价格/资金约束 |
| TOP50 部分/全部换股 | 新股按缺口买、旧股明确退出，卖不掉的旧股保留责任 |
| 股票与 ETF 之间切换 | 日期、数量档位、价格档位、费用和估值各自正确 |
| Hydra 与 V713 同时买同 ETF | 独立目标与资金预留，实际成交归属正确，合计不超券商资源 |
| Hydra 持 ETF，V713 新建相同 ETF 头寸 | 不把 Hydra 持仓当 V713 已完成目标 |
| V713 卖 ETF，Hydra 仍持有 | 只卖 V713 可卖份额，不侵占 Hydra；停用 V713 不取消 Hydra 单 |
| Hydra 有昨仓，V713 当日买入同一 T+1 股票 | 即使券商账户仍有物理可卖量，V713 也不借用 Hydra 昨仓额度卖掉其当日新买数量 |
| 下单已被券商接受但响应丢失 | UNKNOWN 不重复提交且仍占资源；恢复后以券商证据确认 |
| 部分成交、撤单晚成交、收盘仍报 50/55 | 实际成交累计入账；日终未成余量有终局；下一次仅补剩余缺口 |
| 重复快照、成交、进程/服务重启 | 不重复建周期、下单、扣款或分红；缓存不能跨策略串用 |
| 全局暂停、策略暂停、断网缓存、人工单 | 所有提交路径按同一授权和限额判断；事实采集与恢复证据连续 |
| 月末、长假、迟发布、日历不足 | 日期符合已确认 policy；不足时显示明确等待或失败，不猜交易日 |
| 股票/ETF 费用和券商差额 | 估算与实付分开；更正幂等；账户与两个子账本可独立核算 |
| 增资、划拨、分红、送转或缺价 | 资本流不算收益；权益不丢失；无法确认时明确挂起，不伪造 NAV |
| 升级与机器恢复 | 同周期仍用旧冻结 policy；新版本能读原日志；未决订单和资金占用不丢 |

测试中的成交、资金和持仓应使用合成场景或服务器上的隔离研究/生产副本。原始行情、账户明细和大型研究输入继续留在 qmt，仅回传汇总；生产库分析只读。
