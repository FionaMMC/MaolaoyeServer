### 影子账本的持续缺陷

生产历史目标逐证券权重核验：8/10、8/17、8/24、8/31 与前次权重相同，9/14 与 9/7 相同；但日期/输入哈希变化触发重新配平。对应 8/11、8/18、8/25、9/1、9/15 的额外模拟费用共 **1,584.47 元**，其中 9/15 为 **443.50 元**。

这证明了“没有新策略目标但重新交易”的机制。它是 Shadow_Base 的模拟成本，不是券商实际手续费，也不是去掉这些费用后的完整反事实收益（路径和持仓漂移会一起改变）。

本地修复：相同 as_of_date、证券与权重的重新发布只更新来源记录和估值，不重新配平；新月份仍可调仓。Base 直接包装已验证主篮子，取消默认选股 AUM 不同导致的对照偏差。

## 2. 九月为何延迟

已查生产工作日志与订单时间：

1. 8/31 17:30 启动周任务，19:03 结束；candidate 仍为 as_of=7/31。生产器要求 as_of 的月份早于 decision_date 所在月，故把 8/31 当决策日期时排除了刚收盘的八月。
2. 定时器仅每周一运行，因此 9/1 没有再次刷新；9/7 18:26 才发布 as_of=8/31 的目标。
3. 刷新晚于现有 16:00 管线时段，发布脚本也没有衔接单独的订单生成。首批九月 713 订单于 9/8 19:51 创建，有效日为 9/9；未查到有效日为 9/8 的 713 订单。9/8 为什么直到 19:51 才触发的进程级原因，现存日志不足以进一步确定。

本地修复：每个工作日 17:30 检查，20:00 重试；由交易所日历确认下一交易日和已完整结束的月份，已发布当月不重复重训。月末收盘后用下一交易日作为目标执行日期，不引入未来行情。新目标发布后仅运行 paper_v79 订单生成；其他策略组的订单、映射和成交受保留测试覆盖，已领取/已结算/未对账保护继续生效。已发布而后续中断时可重试完成 Base 同步，不重算已消费目标。

日历参数以 [Tushare trade_cal 官方说明](https://tushare.pro/document/2?doc_id=26) 为依据；缺少确认的下一交易日会报错，不用普通工作日猜测长假。

本月残余问题未被强行重发：当前状态还保留未完成目标数量，9/21 的普通管线已记录 stale_consumed_basket。上线修复不会恢复旧失效单；余量结案仍须确认实际成交与终局。
