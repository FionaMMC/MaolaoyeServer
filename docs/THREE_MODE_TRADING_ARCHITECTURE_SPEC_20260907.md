## 1. 先把结论说清楚

目前确实存在不合理的防御，但同时也存在资金保护没有闭合的地方。正确方向既不是继续堆闸门，也不是整体放宽，而是：

1. 三个盘使用一致的策略、账务、数据口径；执行事实来源和权限不同。
2. 真实到账、成交、撤单回报先被可靠接收，再判断如何入账；不能用交易开关拒收事实。
3. 账户的钱、策略的钱、已经交给执行器使用的钱，分三层管理。
4. 服务器负责目标、数量、限价和补单；Windows 负责按批准的执行包操作 QMT、保管执行中的额度和回传事实。
5. 一个策略或一笔订单有问题，只冻结真正受影响的能力；不能顺带停止所有查询、收账和其他策略。
6. 不重写所有代码、不先上微服务。采用一个模块化交易核心，API 与重计算分进程，同一物理账户一个执行协调器。

一句话：**对未来动作严格授权，对既成事实如实记录，对异常按影响范围处理。**

这里的“如实记录”不是无条件相信任何输入。身份、账户、格式、大小限制仍然在；来源可信但业务归属不清的事实进入待认领区，而不是直接给某个策略增加购买力。

## 3. 三个盘各自的规则

### 3.1 定义及边界

| 规则 | Shadow 影子盘 | QMT 模拟盘 | Live 实盘 |
|---|---|---|---|
| 目的 | 测策略经济表现及模型假设 | 测券商通路、状态机和运维 | 管理真实资金 |
| 订单流向 | 仅虚拟撮合器 | 明确绑定的券商模拟账户 | 明确绑定的真实账户 |
| 成交事实来源 | 版本化撮合模型生成的虚拟事件 | 模拟柜台回报、成交与交割 | 实盘柜台回报、成交与交割 |
| 初始资本 | 显式设置的虚拟资本事件 | 模拟账户资金中的明确划拨 | 真实资产中的明确划拨 |
| 可用资金 | 虚拟账本与撮合模型 | 策略额度 ∩ 模拟账户实际可用 | 策略额度 ∩ 实盘账户实际可用 |
| 部分成交/拒单/撤单 | 由模型明确模拟，不冒充券商事实 | 必须保留实际模拟柜台状态 | 必须保留实际实盘柜台状态 |
| 收益、费用、股息 | 有版本的假设值，清楚标识 | 模拟成交与费用，注明局限 | 真实成交，费用从暂估更正到交割 |
| 计算故障 | 停该实例新模拟动作，保留历史 | 停受影响实例/账户的新增动作 | 同左；不停止已知事实的接收 |
| 重跑/重置 | 新 simulation run 可重放 | 新测试 session 可重置虚拟起点，历史留存 | 禁止用重置抹去真实资金与委托 |
| 外部写权限 | 无券商凭据，无执行接口能力 | 仅 paper 账户 | 仅批准的 live 账户 |
| 能否证明实盘可用 | 不能 | 不能完全证明真实柜台规则 | 需要实际部署和受控验收证据 |

建议使用明确的 `book_domain=shadow|paper|live`，每个账户、账本、事件、订单、任务都带域。不是给旧 `execution_domain` 随意增加一个值后让 shadow 走实盘路由；shadow 的执行输出类型在程序和权限上都不能送给 BrokerGateway。

### 3.2 共用哪些，不共用哪些

共用：策略输入/输出协议、数据注册表、金额与数量类型、账务分录、估值、资金预留、订单状态语义、幂等与恢复协议、报表定义。

不共用：凭据、QMT userdata/session、可写目录、本地状态库、操作系统任务身份、账户授权、成交事实源、交易时段和撮合能力假设。

同一个策略算法在三盘运行，创建三个 `strategy_instance_id`；其模型参数可以一致，但持仓与现金分别累计。**不能把影子持仓自动复制成实盘持仓，也不能把 QMT 模拟账户的成交导入 live。**

模拟盘不是“简化到失真”的 live：同样演练部分成交、等待、恢复和资金隔离。模拟柜台支持能力由适配器声明，不能假定与真实柜台完全相同。

### 3.3 Shadow 的特殊约束

1. 以 `simulation_run_id + model_version + input_versions` 标识实验；旧结果不覆盖，修订后新建 run/revision。
2. 必须定义信号何时可知、何时成交。用收盘数据产生的信号，不能不加说明就按同一收盘价假装已经成交。
3. 撮合器明确价格、成交量、停牌、整手、费用、交易日和可卖规则。理论全成可以作为一种模型，但结果标签必须写 `idealized`。
4. 默认只读数据及自有 shadow 账本，不导入券商交易实现。持仓估值与新信号生成分开：新 target 缺失不应阻止旧持仓的可计算估值。
5. 当前 `ShadowLedgerService` 有良好的 no-order 边界，应保留。其直接修改余额、覆盖同日 target、混合 target 有效性与估值的方式逐步换成版本化模拟事件，不先重写策略。

## 4. 六类对象，不再挤在一个 status 或一份 env 中

| 对象 | 含义 | 谁可以创建/改变 |
|---|---|---|
| 事实 Observation | 券商或数据源报告了什么，尚不等于已归属 | 有权限的采集端创建；原文不可覆盖 |
| 账务 Journal / Position lots | 资产和费用归谁，发生了哪些变动 | 账务服务按事实和审批生成分录 |
| 目标 Target | 策略希望持有的组合，绑定输入和决策时间 | 策略生产器发布，政策校验后批准 |
| 执行计划 Rebalance / Attempt | 为目标分几次执行，目标份额与本次差额 | 服务器交易核心 |
| 执行授权 Execution grant | 特定执行器在期限内能动用哪些钱、份额和订单 | 服务器预留后签发/交付；本地管理已授予资源 |
| 工作流 Job / Receipt | 下一步是什么、是否已成功、如何重取结果 | 服务器/客户端各自的持久工作流 |

target、rebalance、attempt 的层级保留：月度目标不是每天重做，补单不是重复消费月度目标。`order_id` 不等于 broker order ID，`fill_id` 也不等于 order ID。

身份至少包含：`domain / physical_account_id / strategy_instance_id / target_id / rebalance_id / attempt_id / order_id`。账户使用内部 ID 和受控别名；真实账号留在私有映射中。不能再靠 `account_alias=None` 的通配含义在 live 中猜账户。

同一物理账户的 canary 也要归入一个明确的小额测试子账本，不能因名称叫 canary 就绕过资金和未决委托占用。

## 5. 资金制度：一份归属总账，外加券商控制快照

### 5.1 三种“钱”

1. **物理账户资产**：券商实际持有的钱和证券，是所有策略共同受约束的外部事实。
2. **归属账本**：其中多少属于策略 A、策略 B、未分配储备、外部/人工持仓或待认领差额。
3. **执行中资源**：归属不变，但哪些钱/证券已预留、已交给离线执行器、已挂单或提交结果未知。

未分配储备必须是有流水的真实账本分区，不再随时用“QMT 可用现金 − 各策略余额”算一个差值就当成可分配资本。后者只能作为诊断，不是入账凭证。

资金归属分区建议为 `STRATEGY`、`RESERVE`、`EXTERNAL`、`SUSPENSE`。`SUSPENSE` 表示已经观测但归属/分类待核实的差额，默认不得增加购买力。正差额也不能自动送给 Hydra；负差额不能隐藏为零。

### 5.2 现金字段契约

| 字段 | 用途 | 禁止的用法 |
|---|---|---|
| `broker_available_cash` | 此刻券商允许购买的金额 | 当作策略净资产或全账户账面现金 |
| `broker_frozen_cash` | 已被券商冻结的金额 | 当作损失；与本地同一委托预留重复扣除 |
| `broker_withdrawable_cash` | 允许转出金额；来源未提供则 unknown | 从 available 猜出来；据此自动调用资金划转 |
| `ledger_cash` | 按已入账事件形成的现金资产 | 因下单预留就直接当作已花掉 |
| `receivables / payables` | 已确认经济权利/义务，尚待实际支付 | 把应收股息当可花的现金 |
| `confirmed_spendable_cash` | 本策略归属且已满足券商可用规则的资金 | 包含未成交卖单的预计回款 |
| `reservation` | 对未来使用的承诺，非费用和损失 | 向两个执行器重复发放 |

所有快照必须包含来源、读取开始/结束时间、柜台/接口版本、交易日、来源序号或观测 ID、完整性。QMT 多次查询不天然构成同一瞬间的原子快照；读中发生交易时记录不一致并重取，不能无条件比较到分并判账坏了。

不能通用地写死 `总现金 = cash + frozen_cash` 或 `总现金 = total_asset − market_value`。具体柜台的字段定义、在途款项及费用时点先验证，适配器输出规范化结果；不能验证时标记 unknown，用成交/资金流水与交割单建立可解释桥接。

### 5.3 必须成立的守恒条件

在同一已对齐的账务时点与资产口径下：

```text
账户账务现金 = Σ 策略现金 + 储备现金 + 外部现金 + 待认领现金
账户证券数量(code) = Σ 策略归属数量(code) + 外部数量(code) + 待认领数量(code)
内部资本划拨对全账户的现金净影响 = 0
每笔已发布分录：借方合计 = 贷方合计（逐币种）
每笔已确认成交：归属数量合计 = 成交数量；归属费用合计 = 该笔分摊费用
已授予的资源，不能同时作为服务器未预留资源再次分配
```

再把“账户账务现金/证券 + 明示的在途与时点差异”与券商控制快照对齐。**账平**和**资金足够**是两个检查：差一笔无法解释的 100 元，不会因账户还有 1,900 万就自动变成账平。

守恒等式中的待认领分区不能成为永久掩盖错误的桶：每项差额有来源、影响范围、处理责任人、年龄和处置记录。自动进入待认领区不等于允许新交易或宣布对账完成。

### 5.4 资金归属与收益

```text
策略 NAV = 归属现金 + 原价持仓市值 + 应收款 − 应付款
策略期间投资损益 = 期末 NAV − 期初 NAV − 期间净外部资本划拨
```

这里“外部”是相对于策略账本：储备划给策略属于策略资本流入，但不属于物理账户入金。持仓涨跌、归属交易盈亏、股息、费用留在原策略；不能每日把它重置到最初 21.1 万，也不能自动吸收账户其他 1,900 多万。

现金、费用和货币分录用定点数；最终 CNY 支付到分，高精度单价/费用计算用 Decimal 并保存舍入规则。数量为整数，成本分摊保留足够精度。数据库不可依赖二进制 float 的相等比较实现账务幂等。

### 5.5 分录例子：真实发生与内部划拨分开

以下是设计示例，不是实际账务数据：

| 事件 | 分录/归属结果 | 对策略购买力影响 |
|---|---|---|
| 账户到账 190 万，确认属于未分配储备 | 储备现金 +190 万，对应外部资本 +190 万 | Hydra 不变 |
| 审批储备给 Hydra 5 万 | 储备现金/资本各 −5 万，Hydra 现金/资本各 +5 万 | 新的可用授权可增加；旧离线包不自动扩大 |
| 买入成交，价款 10,000，费用暂估 5 | 归属证券成本 +10,000，费用 5；记录现金支付或对应交易应付款 | 立即扣减/保留所需资源，不能重复消费 |
| 正式费用为 4.80 | 用关联原成交的费用更正释放 0.20 | 完成确认后归原策略 |
| 分红权益确认但未到账 | 应收股息 +D，股息收益 +D | 不增加可花现金 |
| 分红到账 | 现金 +D，应收股息 −D | 仅增加权利所属策略的已确认资金 |

成交时直接减少现金，还是先记录交易应付款再在柜台资金生效时结转，由 `cash_recognition_policy` 明确定义；不能两种方式同时记一次。成交与资金流水描述同一笔买卖时，流水用于核销/确认，不能再扣第二次现金。任何未支付义务都计入购买力扣减。

## 6. 入金、出金、划拨、初始化：四种不同流程

### 6.1 收到真实资金变化

```text
采集到资金流水 → 身份/格式校验 → durable inbox 返回 receipt
→ 核实来源与去重 → 分类到储备、策略收入或待认领
→ 原子入账 → 更新余额投影 → 触发对账/待办
```

常规到账默认进储备。明确带策略资本授权的到账，也应保留“外部到账”和“内部划拨”两个关联事件，不能只留一笔 Hydra DEPOSIT。

这里的“核实”优先由已批准的数据源、稳定事件编号、账户匹配和分类规则自动完成，**不要求每笔入金人工点一次批准**。只有冲突、来源不足或无法自动归属的项目进入待办；补到证据后自动重新处理。持仓正常盈亏、已确认股息不需要每天重新审批策略预算。

接收时不要求：本月无 target、全部 canary 已终局、所有策略已对账、订单生成开关开启、研究数据完整。

来源尚未充分核实：`RECEIVED_PENDING_VERIFICATION`。归属不清：`UNATTRIBUTED`。可靠事实导致负差额：照实保存事实和问题；暂停受影响的风险增加动作，不抹掉负数或给它编一个充值解释。

### 6.2 内部资本划拨

`allocate(reserve → strategy)` 必须有分配权限、正数金额、幂等 request ID、已确认储备余额，且不占用已委托/已授出的资源。目标策略存在且处于可接受划拨状态即可；不要求整个账户没有旧订单。

`deallocate(strategy → reserve)` 只能从该策略没有被冻结、已授权、应付或未知委托占用的现金中退出。持仓资产不能当现金直接退回；若需减仓，另建明确的减资执行计划。不能偷偷改变原 target 来满足提款。

有挂单并不意味着完全禁止划拨。应只拒绝超过该策略**未承诺余额**的部分；返回具体缺口和占用来源。等待某份 grant 释放时记录 `WAITING_RELEASE`，不能让 API 服务退出。

划拨已登记，但旧 grant 仍有效时，新增资金不进入旧包；可在下一次批准的 grant 中使用。负向划拨不能撤走旧 grant 的钱后仍让它在离线状态下照常有效，见第 9 节。

### 6.3 提款

本轮不新增自动调用券商资金转出功能。未来若提供“发起提款”，它是授权命令，必须检查可取资金、归属、冻结和已发放额度。

但“人已经在券商提款了”是事实采集：即使提款侵占了策略资产也必须留存。根据可证明的来源归属入账；无法归属时建立差额案件和必要的账户级限制，不能把它拒绝后仍显示旧余额可花。

人工柜台操作绕过本系统时，任何软件子账本都不能保证物理资金不被挪走。要实现强隔离，需要专用物理账户，或约定人工操作流程并使用本地账户级协调；不能用更多 hash 宣称解决这件事。

### 6.4 初始化

初始化只建立一次期初余额及归属，输出不可变 `opening_receipt`。已经初始化的实例再收到同请求，返回原回执和另外的当前状态；不拿交易后的当前余额与期初余额作相等校验。

修改期初错误使用可审计更正或迁移，不覆盖真实成交历史。正常入金、股息、划拨不走初始化，不需要重新打开初始化闸门。

已有 attributed 迁移不得重复执行历史退资：9 月 6 日快照里 Hydra 已切换 attributed，并保留了原 DEPOSIT 与 CAPITAL_DEALLOCATION。迁移需读 journal 的事件 ID，不按聊天里的约数重放。

## 7. 多策略共享证券、费用与资源

### 7.1 归属不是按代码排他

A 和 B 可以都持有 510300。数据库记录各自 lots、来源成交及成本；账户对账看它们的合计和外部归属。不能规定“只要 A 用过这个代码，B 就不能用”。

卖出上限同时受三层约束：

```text
已批准的卖出数量
策略归属且按适用品种/交易日规则可卖、尚未授权给别处的份额
券商此刻该证券可卖数量，扣除尚未反映在快照里的本地在途认领
```

已有持仓不一定全部可卖；不能用全账户的 T+0 可卖份额，替代某个策略 T+1 新买份额的归属可卖性。交易规则按品种/市场/柜台政策记录，不把所有 ETF、股票都当成同一种规则。

### 7.2 归集与分摊

建议第一版先保持每个策略的逻辑订单与归属明确；是否合成一个 broker order 是后续可选优化。当前订单归集可用兼容层保留，但必须提前冻结分配明细。

合单时规定：同域、同物理账户、同方向、同执行政策才可归集；成交按预定规则分配，例如按剩余批准数量比例及确定性余数顺序。每次增量成交均分配，余数不能凭处理顺序随机归属。费用总和必须精确守恒。

A 买、B 卖不能在本地虚构两笔成交抵消，也不能随意同时挂相反委托。账户协调器识别冲突；初版串行执行或延后冲突腿，并记录理由。未来若做内部持仓转让，需单独批准转让价格、资本/损益和税费口径，不能伪装成真实券商成交。

### 7.3 账户级单写者

同一物理账户只能有一个获准发出交易写调用的执行协调器。它管理该账户所有策略的提交、撤单、资金认领和恢复；策略逻辑不在里面。

**v1.1 补清：单写者不等于一张单占住整个账户的长任务锁。** 资源认领与状态写入使用短事务；等待卖款、成交、服务器恢复时持久化为等待状态并让出调度，不持有数据库事务或阻止执行器处理其他事件。撤单请求与未知提交的恢复核实优先于新下单；事实接收、已知成交记账也不得排在“等这一单结束”的后面。

账户协调器在每次新的写调用前重新检查对应资源认领和当前操作许可，不让多个 worker 绕过它同时发送交易。单个券商调用需有界；如果调用超时后的执行结果未知，记录未知状态并查询恢复，不能为了让队列继续而盲目启动第二个写入者。支持独立回报/查询通道时按经验证的适配器能力使用；不假设 SDK 天然支持并发交易写调用。

不同物理账户、paper/live 可以分别运行，不共享本地锁和状态库。单机用 OS 进程互斥加 SQLite 原子认领；多机不能靠一个 server lease 到期就允许第二台接管，因为旧机器可能仍能离线下单。

跨机器接管需完成旧执行器停用/交还、券商未决核实和状态转移。在不能证明旧执行器已失去写能力时，不能签发冲突额度给新机器。可用性退让发生在该账户写入，而不是整个 server。

## 8. 从数据到目标、数量和价格

### 8.1 数据与日期

每份输入显式声明 `source / source_version / adjustment / as_of / available_at / coverage / revision / digest / quality`。

- 模型用批准的复权口径；Hydra 已批准为 QMT HFQ。
- 交易数量、限价、成交价和持仓估值用 raw。
- 公司行动单独记录；不能在已含分红的复权收益上再叠加一次分红收益。
- `decision_time`、`data_as_of`、`execution_trade_date`、`event_time`、`settlement_date` 分开，市场时钟显式 Asia/Shanghai。
- 数据清洗不静默补零、不把缺数据当停牌、不删除异常后声称覆盖完整。只检查当前策略实际依赖的数据；其他策略不受无关标的缺数影响。
- 修订创建新数据版本；重跑绑定版本。批次发布前原子更新数据索引，不覆盖执行中的原始文件。

### 8.2 策略输出

统一输出 `HOLD / TARGET / CASH_TARGET / FAILED`，其中 FAILED 不能变成空列表冒充无操作。现金目标是合法业务结果，与“没收到 target”不同。

策略输出权重与意图，不调用 broker、不直接改账本。策略内部递推状态必须与本次决策 revision 绑定，不能“状态先提交、订单后失败”而重跑时再推进一遍。

普通 pipeline 与 Hydra relay 都转换为相同核心协议，保留各自决策算法。月度/周度/每日节奏是策略政策，不是三盘模式的区别。

### 8.3 Hydra 数量与资金规模

Hydra 月度初始 target 以策略自身 NAV 及同一份 raw 价格确定目标份额，按批准的整手、费用和价格缓冲规则取整。价格带不是额外资本；NAV 也不是现金购买力。

现有 Hydra 9 ETF 白名单、研究桥接不准交易、50bp 限价保护属于已确认业务规则，保留为版本化 Hydra 政策；不成为所有策略共享核心的硬编码。

目标冻结后，普通 residual 保留目标份额：

```text
residual(code) = frozen_target_shares(code) − 已入账的策略实际份额(code)
```

这只是差额意图，还要经过实际可卖、可用资金、交易日、公司行动、在途订单与价格政策检查才可变成本次订单。资本变动或公司行动需要改变目标份额时，创建关联的 target amendment，不直接改原目标。

“达到 80%”分别报告：投资仓位覆盖、非零目标名称覆盖、权重偏差、订单/换手保真。使用多期冻结输入测不同资本规模的分布，不用单次 9 笔都能凑一手就宣布资金足够。不得为补齐笔数借用储备。

### 8.4 服务器负责补单定价

补单留在 server：用已结案事实、同一批准目标、当前可用 raw 版本和策略资本，生成下一有效执行日的剩余订单。

客户端不重新算权重、target 股数或自行追价。补单的 raw hash、target ID、rebalance ID 由批准的业务记录自动关联，不再每周期手填三项 env。

草稿计划绑定一个 `book_cut`；发布前如果相关持仓/资本已变动，废弃未发布草稿并重算。已经批准的 target 份额不因普通价格波动自动重算；已经下发的 grant 更不能被新草稿覆盖。规划预留到执行授权是同一资源记录的阶段推进，不做两次资金扣减。

初次和补单的价格参考政策必须清楚区分：更新 raw 可以给下一 attempt 新限价，但必须保留月度决策价、前次参考价和累计执行偏离；不能靠每天换参考价掩盖总滑点。超过已批准价格政策，等待/拒绝该订单，不偷偷放宽。

## 9. 晚间核对与次日离线执行：额度必须闭合

### 9.1 preflight 的最终职责

晚间 preflight 是“核对并领取一份有资源保障的执行授权”，不是盖一个成功章后第二天随意使用 QMT 全账户现金。

步骤：同步可得的券商事实 → 明确账务及未决影响 → 读取完整不可变批次 → 校验目标/数据/账户/价格/日期 → 原子预留现金和可卖份额 → 发布绑定执行器的 grant → 客户端本地原子保存。

grant 至少带：协议版本、域、账户、实例、执行器身份、批次 ID/hash、目标链、允许的订单、资金及证券上限、费用政策、交易日/有效窗口、政策版本、资源预留 ID、依赖资源版本、幂等 ID。

不要求“全账户所有字段与昨晚一模一样”。未分配储备新到账、别的已隔离策略分红、报价导致总资产变化，都不是批次内容被篡改。

### 9.2 什么变化会使授权失效

| preflight 后变化 | 处理 |
|---|---|
| 储备到账增加 | 记账；旧 grant 不变，不扩权，也不要求整包重做 |
| 其他策略在独立额度内交易 | 继续；账户协调器更新全账户可用约束 |
| 同策略新增资本 | 记划拨；旧 grant 仍按原额度，新增授权另行批准 |
| 打算调走已授予给本策略的资金 | 等待交回/撤销确认，不直接生效并重新分配 |
| 同策略持仓被人工卖掉、强制扣费形成缺口 | 本地重新核算受影响资源；阻止冲突订单，保留事实并报告 |
| 股票拆并份额、交易规则变化影响授权数量 | 暂停受影响订单，等待经批准的修订；不本地猜数量 |
| QMT 不可用或账户身份不同 | 不能提交；不是通过读 server 可以补救的事情 |
| server 不可用 | 有有效本地 grant 则不影响既定离线执行；回报本地排队 |

不能用一个“全账户每发生一笔流水就加一”的版本号使所有 grant 失效。使用明确的资源预留和受影响版本；共享资源的真实冲突才传播。

执行器仍须通过本地已保存观察、券商可获得事件和当前快照，核查授权水位以来影响本账户资源的变化。**只看当前物理余额很大，不能证明策略自己的资产没有被挪用。** 无法确定某次人工/外部变化归属时，形成影响分析；不能证明某份 grant 仍有资源保障，才暂停其新动作。不是要求原快照字面完全一致，也不是要求再上线问 server。

### 9.3 购买力，不借用账户里的别人的钱

本地维护每份 grant 的独立资源账：

```text
grant 剩余现金能力
  = 初始已拨入的可花现金
  + 此 grant 获准归属且已确认可用的卖出净回款
  − 已确认买入支付与费用
  − 尚未终局/提交未知订单的剩余最坏支付占用
  − 其他已知应付与需保留费用

可提交买单上限 = min(grant 剩余能力, 券商实时可用能力)
```

资源在 `SERVER_RESERVED → DELEGATED → LOCAL_CLAIMED → BROKER_HELD → CONSUMED/RELEASED` 之间转移。它们是同一笔资源的状态，不是每层重复扣一遍。一个风险占用单位必须有唯一 ID 和唯一权威管理方。

QMT 快照可能尚未反映刚提交的冻结/扣款。本地协调器保留这些 in-flight 占用，直到对应 broker observation/资金变化已被对齐；不因连续两次 QMT 都显示旧余额就重复买。已经包含在 QMT available 中的冻结也不再重复扣减。

“先卖后买”必须是依赖已确认回款，而非调用顺序：SELL 被拒、只成交一部分、尚待成交时，只使用实际已实现且可用的归属净回款。物理账户即使有 1,900 万闲钱，也不能垫给 Hydra。

服务器可以预先批准依赖卖出回款的买单及拆分子单；本地只根据资源就绪执行已批准子单，不自行修改数量。资金不足返回 `WAITING_CASH`，有界等待到该策略的提交截止；仍不足则留给后续 residual，不能盲目自动重试下单。

### 9.4 授权到期不等于资源可以回收

到期只表示不能再开始新的委托。已发出的单、提交未知的单和未回传成交仍有影响；服务器不能因 lease 超时或没收到 ACK 就自动把钱发给另一个策略/执行器。

grant 一旦已签发且可能到达客户端，就保持占用。服务端响应丢失可按原 request ID 重取原 grant；不能另造一个。释放需客户端持久交回记录和订单终态/资源核实，或人工完成具证据的接管程序。

服务器停止新生成，不会神奇撤销 Windows 已经缓存的授权。这是离线可用性的明确代价：急停需要触达本地执行器，或停用该执行器的实际写能力。UI 必须显示“server 已暂停新授权，但某些已签发 grant 仍有效”。

同一账户的当日执行计数和金额上限跨所有 attempt 累计，包括已发生、活动和未知占用；不是生成一个 residual 批次就把每日限额清零。服务器与本地对同一已委托资源共享标识和交接水位，分别保存审计副本，但不能同时各自释放/再分配。

## 10. 委托生命周期：状态、成交和结案分开

### 10.1 三个维度

| 维度 | 示例 | 关键规则 |
|---|---|---|
| 提交意图 | PREPARED / DISPATCH_UNKNOWN / ACKNOWLEDGED / DEFINITELY_NOT_SENT | 未知必须恢复，不盲目重发 |
| 券商活动状态 | ACTIVE / CANCEL_PENDING / TERMINAL_CANCELLED / TERMINAL_FILLED / TERMINAL_REJECTED / UNKNOWN | 来自券商证据，不从日期推断 |
| 成交事实 | 多笔 execution，或带覆盖范围的累计数量/金额 | 已成 100 与剩余已撤可以同时成立 |

QMT 的 53“部撤”与 55“部成”不是同一终态：前者剩余已撤，后者仍待成交。当前映射成一个 PARTIAL 必须改。撤单调用的返回不代替后续终态查询。[迅投委托状态说明](https://dict.thinktrader.net/nativeApi/xttrader.html)

### 10.2 正确的提交顺序

1. 校验本地包、账户、时间、价格/规则和资源；能在无副作用阶段确定失败的，返回明确未发送。
2. 本地事务认领订单和资源，持久记录即将调用 broker 的意图；提交事务之后才能发出券商调用。
3. 调用一次。收到明确编号或明确拒绝后持久记录；网络/进程中断等不确定情形进入 DISPATCH_UNKNOWN。
4. 恢复时按稳定 remark、账户、证券、方向、数量等核查已存在委托。找到则关联；找不到也不能仅凭当日查询空就断言历史没下过。
5. broker 历史查询能力不足时，用已保存回报/交割证据处理；必要时等待人工确认该单。不能“强制重跑整个批次”解决未知。

连接阶段可以有界重试；交易写调用不能因一般异常被自动重试。跨日同一逻辑订单的 ID 保持可追溯，补单创建新的 child order ID，不冒充原 broker order。

### 10.3 事实接收逐项推进

一笔仍 ACTIVE，不妨碍其他八笔成交入账，也不妨碍上传该笔已成交的部分。每项 observation 单独有处理结果；批量入口不能因一个待处理项回滚所有已知且独立的事实。

优先接收逐笔 broker execution ID 并去重，保留原委托状态观察。若只有累计成交快照，则按来源流及覆盖水位做单调增量转换，记录“临时聚合覆盖”。后续补到逐笔成交时核销该覆盖，不再新增一次现金/持仓。数量相同但状态变化仍须更新状态；乱序旧观察不能回退已确认数量。

同一券商编号可能跨账户或交易日复用：唯一键至少包含域、账户、来源、适用交易日和来源事件编号；由适配器声明实际唯一范围。冲突载荷隔离为问题，不直接丢弃或覆盖。

已发生的成交即使造成策略超支，也要入事实账并产生赤字/差额处置；不能成交表写 FILLED，归属账本静默跳过，然后重试又因去重无法修复。

## 11. 撤单、结案与补单工作流

### 11.1 时间只负责唤醒

当前仓库候选任务是 14:55 cancel、16:05 settle-close、16:20 retry、18:00 query/preflight、下一交易日 09:10 submit。**这些不是本轮确认的现网任务，也不是所有市场通用规则。**

目标工作流按券商政策配置时间窗口、截止、等待间隔、最后期限与日历版本：

```text
已提交 → 持续/定期采集回报
→ 撤单窗口内请求撤回剩余 → 等待券商终态
→ 已知成交归属入账 → 资源核实 → attempt 交易结案
→ COMPLETE 或 RESIDUAL_READY
→ server 生成下一执行日差额 → 晚间领取新 grant → 次日离线执行
```

调度器不承载资金计算，只调用“推进到当前可完成状态”。16:20 被唤醒但 broker 尚未终局，返回 WAITING_BROKER，保留补单意图；close 后按工作流依赖再继续，不要求人工把几个时间重新对齐。

### 11.2 撤单政策

- 只撤本执行器/授权范围内的委托；人工单、其他策略的单不自动全撤。
- 每笔写调用前再检查撤单窗口；不能只在脚本入口检查一次后无限运行。
- 查询与写调用有超时；发起撤单后保持占用，直到券商明确终局并核对累计成交。
- “今天收盘了”“QMT 查询没返回”“撤单请求返回成功”都不等于委托已撤。
- 具体截止以券商、市场、订单类型的有效政策和受控验证为准；保留同事反馈的券商限制，不把它推广为全国统一规则。

### 11.3 结案有两层

**交易结案**：该 attempt 不再有活动/未知写入；累计成交已覆盖，归属持仓可解释，资源可以确定释放或保留，能够计算 residual。

**财务最终化**：正式交割费用、税费、股息等核清，日终净值可发布为 final。可能晚于交易结案。

如果只有小额费用待最终化，可以在有明确暂估上界和足额预留的情况下交易结案；费用超出估算时照实记账并处理缺口。若未知成交数量/持仓归属，不能同样降级为费用估算问题。

`COMPLETE` 指目标份额已达到或按明确政策处理完，不表示所有长期财务事项永远不会修订。若因整手/不可交易等不能实现，标记原因及授权豁免，不用 COMPLETE 掩盖差额。

### 11.4 哪些旧订单会阻止补单

同一 rebalance 的冲突未决订单必须先处理。另一个实例的已隔离订单，不应仅因在同一数据库就阻止 Hydra；但共享证券/资金的未知占用无法排除时，扩大到该资源或该物理账户的新风险。

跨月新 target 到来，也不能覆盖旧活动 attempt。先完成交还/撤单或显式 supersede 工作流；原目标、订单和事实留存。

## 12. 估值、分红、收益和执行质量

### 12.1 日终估值独立运行

每个启用实例即使没有新订单，也要按自己的持仓和估值政策产生日终记录。退休实例停止新的绩效发布或明确标注 inactive；不继续装作活跃策略。

缺价格不按零估值：输出 `INCOMPLETE` 或注明时点的 `STALE_ESTIMATE`。交易已结束但账务未齐，输出 provisional NAV 与缺失项；不能当 final。报告失败不回滚已发生交易。

日终快照包含 book revision、event watermark、价格版本、费用状态、现金/持仓/应收应付、资本流入流出、NAV、质量与未解释项。后续费用修订新增 revision，保留旧版本。

### 12.2 收益计算

增资不等于盈利，减资不等于亏损。优先在资本流发生前后取可用估值，计算分段 TWR；也可采用有相同准确估值边界的份额净值法。若仅有日初/日末和资金时间，使用明确标注的 Modified Dietz 估计，不冒充精确 TWR。

```text
TWR = ∏(各不含外部资本流的子期间增长因子) − 1
Modified Dietz = (V_end − V_begin − Σ flow_i)
                 / (V_begin + Σ time_weight_i × flow_i)
```

分母非正、缺可靠估值或资金时间时显示不可计算及原因。股息是投资收益，不从收益中作为资本流扣掉；应收转现金不再计一次收益。物理账户报告的外部入金与策略报告的内部划拨分别列示。

上述选择参照 GIPS 对现金流时点估值与近似收益方法的区分；不是宣称本系统已经符合 GIPS 全部要求。[GIPS Asset Owners Handbook](https://www.gipsstandards.org/standards/gips-standards-for-asset-owners/gips-standards-handbook-for-asset-owners/)

### 12.3 公司行动

分红按登记日归属份额确定权益，而不是付款日谁还持有就给谁。拆分/合并改变数量和单位成本，不凭空创造收益；更新 sellability、未完成目标及委托影响，需要关联修订。

四流中的 action 数据、券商实际支付与交割必须可关联。没有支付日不能假装已到账；只有调整因子不能代替真实现金流水。跨策略同一证券按当时权益 lots 分配，舍入余数有确定性规则。

### 12.4 执行质量

每笔保留原始决策价、每次 attempt 参考价、到达行情及源时间、委托限价、成交金额/数量、实际或暂估费用、可用 IOPV 及源时间。区分决策到到达的市场变动、到达到成交的执行滑点和 ETF 溢价。

普通观测字段缺失可以标记质量不足，不阻断已经发生的成交入账。如果某策略明确批准“无实时溢价证据不买”，则只在该策略新买单上执行这项政策；不能把所有 IOPV 缺失都全局 hard fail。

统计按价格、流动性、订单大小与时段分组，离线反馈到研究成本模型；不直接在线自动放宽价格或增加资金。

## 13. 闸门清单：保留、迁移、缩小或移除

`BLOCK` 是拒绝某个新命令；`WAIT` 是依赖未就绪、可恢复；`QUARANTINE` 是保留事实但暂不授予业务效果；`WARN` 是质量/运维提示。不能把四者都变成抛异常并退出进程。

| 编号 | 条件 | 最终处理/最小范围 | 必须仍能做什么 | 对当前实现的处置 |
|---|---|---|---|---|
| G01 | 无认证/越权域或账户 | BLOCK 该请求 | 其他已认证请求 | 保留，不让 pending inbox 成为认证绕过 |
| G02 | shadow 请求券商执行 | BLOCK 该动作，结构性无能力 | shadow 历史读取和诊断 | 保留 no-order 边界 |
| G03 | 目标来源、价格、数量不合规 | BLOCK 该目标/订单 | 旧订单回报、资金事实、其他目标 | 保留；不用全域停机 |
| G04 | 关闭新订单生成 | BLOCK 新 attempt/grant | 查询、事实接收、撤单、结案、报表 | 从 close 移除生成开关依赖 |
| G05 | 本地暂停提交 | BLOCK 新 submit（包括卖出） | 已授权范围的撤单、回报、恢复 | 独立于风险只减仓模式 |
| G06 | 想启用 reduce-only | 另一个显式政策，不是默认逃生通道 | 只允许证明减少归属敞口的批准动作 | 不把任何 SELL 都视为天然安全 |
| G07 | 接收真实入金，存在旧 target/canary | ACCEPT 到 inbox；核实后入储备/待认领 | 继续收账与结案 | 删除业务状态对事实入口的耦合 |
| G08 | 尚未初始化实例 | BLOCK 该实例的首次交易/划拨命令 | 账户级资金事实 | 从现金事实 schema 移除强制实例归属 |
| G09 | 资本划拨超过未承诺余额 | BLOCK/WAIT 该次划拨，列出占用 | 到账、成交、未超额的独立划拨 | 保留真实资源约束，替换 available 比较 |
| G10 | 已发生提款导致缺口 | ACCEPT；待归属/赤字告警；限制受影响新风险 | 继续接收事实和修复 | 不再因不能保持非负就丢事实 |
| G11 | 某笔订单活动或未知 | WAIT 该单/冲突 residual；资金预留保留 | 其他已知成交入账及无冲突动作 | 取消全批回报抛错 |
| G12 | 一笔已部撤有成交 | TERMINAL_CANCELLED + 已成交量 | close、释放剩余、residual | 修复 PARTIAL 语义冲突 |
| G13 | 昨晚后账户新增储备入金 | 不使旧 grant 失效、不扩额度 | 原授权内执行 | 移除全账户快照字面相等要求 |
| G14 | 次日 server 不可用 | 既有有效离线授权可执行 | 本地回报持久化、QMT 检查 | 移除 submit 的 HTTP 健康依赖 |
| G15 | QMT 当前账户不符 | BLOCK 该执行器的写入 | 与正确账户绑定的本地诊断 | 保留，不能为了通路绕过 |
| G16 | 策略自己的现金/可卖不足 | WAIT 受影响订单，禁止借用他人额度 | 卖出回报、资源释放、独立订单 | 补齐本地动态归属能力，不预支预计卖款 |
| G17 | 少量费用待 final | 有上界预留则可 provisional 收尾 | 正式费用补齐与修订 | 从全阻断改为明确财务状态 |
| G18 | 无法解释全账户资金缺口 | 受影响范围不能确定时 BLOCK 账户新增风险 | 事实、撤单、对账、其他物理账户 | 合理账户级硬限制，不假装局部隔离 |
| G19 | 一个策略缺数/插件报错 | WAIT/FAIL 该实例 run | HTTP、其他实例、既有持仓可用估值 | 删除 strict instance 全 pipeline 返回 |
| G20 | 报表/备份/企微失败 | WARN + 独立重试，不变更交易结果 | 提交事实、撤单、结案 | 输出单独质量状态，别假报“未下单” |
| G21 | 同 request ID 内容相同 | 返回原结果；当前状态另列 | 安全重试 | 先查幂等结果再检后续业务状态 |
| G22 | 同 ID 内容不同 | CONFLICT，保留证据待处理 | 其他请求 | 保留，不自动 force 覆盖 |
| G23 | 过执行/撤单截止 | 禁止新的对应写调用 | 查询事实、终态确认、合法恢复 | 不按日期伪造终态 |
| G24 | 版本或配置不兼容 | 停受影响能力/候选发布 | 旧兼容 release、读取/事实同步 | 不要求 server/client 必须同 SHA |
| G25 | 未知大额/异常持仓数据 | 保存原始观察，核实该数据流 | 其他可信来源的事实 | 移除 live 的静默大数量过滤 |
| G26 | 磁盘满/本地状态不可持久化 | BLOCK 新交易写调用 | 有能力时只读核对和告警 | 不能退化为“没查到已下单，所以再下” |

异常不能无限期 WAIT 而无人知道。每个 WAIT 记录 `reason_code / scope / since / next_check / deadline / owner / required_evidence / allowed_actions`。到期限告警升级，但不靠篡改订单状态解除。

权限开关建议只保留少数能力：`accept_facts` 是已认证正常运行能力，不是日常交易闸门；`allocate_capital`、`create_plan`、`issue_grant`、`submit` 分别授权；`cancel/recover/close` 不依赖新交易开关。安全事件中可以停用被盗凭据，但这与业务暂停不同，应有替代的受控恢复路径。

配置按命令加载：读 ledger 不应要求 retry 的 raw hash；回传成交不应要求新单的全部 risk caps；server 某个策略配置不合法只禁用该实例。基础鉴权配置或数据库不可用等全局关键错误仍必须明确报告，不伪装服务可写。

## 14. 最终代码架构：模块化单体，三个清楚的执行边界

### 14.1 进程与责任

| 运行单元 | 负责 | 明确不负责 |
|---|---|---|
| API 进程 | 鉴权、短请求、持久收据、查询、任务提交、健康度 | 在 HTTP 事件循环内跑策略、重写大 Parquet、长时间等券商 |
| Server worker | 策略计算、计划、账务处理、对账、工作流推进、报告 | QMT 实盘交易写调用 |
| Windows account agent | 本地授权包、单账户资源协调、QMT 提交/撤单/采集、outbox | 策略权重、补单算法、增减资本审批 |

初期 worker 可以一个部署单元，但按 account/instance 划分任务；重型研究计算放子进程并设资源限额、超时，不占数据库写事务。交易账务工作优先于报告；某个研究子进程崩溃不拖死 API。

无需先引入 Redis、Kafka、Kubernetes 或若干微服务。先用数据库持久 jobs/outbox 和唯一认领实现恢复。数据量/吞吐证据证明需要时再拆，不以设计名词增加运维面。

### 14.2 拟议目录与模块边界

```text
trading/
  domain/                   # 纯类型与不变量；无 HTTP/QMT/数据帧依赖
    identity.py             # 域、账户、实例、稳定 ID
    money.py                # 定点金额、价格、数量、舍入
    accounting.py           # 分录、lots、权益、应收应付
    capital.py              # 储备、划拨、授权资源状态
    targets.py              # 意图、rebalance、attempt、不可变订单
    orders.py               # 提交意图、broker 状态、成交
    policies.py             # 可组合的策略/账户/执行政策
  application/
    ingest_facts.py          # 验证、接收、去重、待认领
    post_ledger.py           # 归属、核销、分录与余额投影
    allocate_capital.py      # 内部划拨，不调用券商转账
    build_plan.py           # 所有策略统一目标转执行计划
    issue_grant.py          # 原子预留并发放离线能力
    reconcile.py            # 事实/账务/券商三者桥接
    close_attempt.py        # 收尾，不要求新单权限
    build_residual.py       # server-only 差额算法
    workflow.py             # 依赖、幂等、超时、重取回执
    valuation.py            # NAV、资本流、费用与质量
  ports/                    # Repository/UoW/Data/Strategy/Broker 接口
  adapters/
    sql/                    # 事务、约束、存储与投影
    data/                   # 版本化行情、行动与日历
    strategy/               # V20H/V53/V7.13/Hydra 兼容适配
    broker/                 # QMT paper/live 的能力与字段规范化
    shadow/                 # 无券商写能力的虚拟撮合器
server/
  api/                      # 薄路由，调用 application
  worker/                   # 持久 jobs，研究隔离，账务优先
execution_agent/
  cache.py                  # grant 与原始请求原子落盘
  account_coordinator.py    # 单物理账户写入/资源认领
  submit.py                 # 有界、离线、写前记意图
  observe.py                # 回报及券商快照采集
  cancel.py                 # 按执行政策撤自己的单
  sync.py                   # 本地 outbox，server 恢复后续传
  cli.py                    # 每命令加载最小配置
ops/
  release_manifest/         # 版本/协议/迁移/配置兼容
  windows/                  # 任务只唤醒，不藏业务逻辑
  server/                   # 部署、备份、恢复
tests/
  domain/ contracts/ scenarios/ recovery/ windows/
```

这是依赖关系设计，不要求第一轮把现有文件全部搬家。先在旧目录中建立同等模块边界和接口，兼容旧 API；逻辑稳定后再移动目录，避免大规模改路径与修资金问题混在一个发布里。

规则：domain 不导入 adapters；API 不直接修改余额；策略不直接调用账务/券商；agent 不导入模型计算；只有账务服务发布分录，只有 account coordinator 发起该账户的 broker 交易写调用。

### 14.3 最小接口契约

```text
Strategy.decide(inputs, prior_state) -> DecisionRevision
Planner.build(decision, book_cut, pricing_policy) -> ImmutablePlan
Capital.allocate(command, expected_resource_revision) -> AllocationReceipt
Grant.issue(plan_id, executor_id, request_id) -> ExecutionBundle
Broker.observe(cursor) -> Observations + coverage + next_cursor
Broker.submit(approved_order, stable_intent_id) -> Ack | DefiniteReject | Unknown
Broker.cancel(owned_broker_order, policy_window) -> RequestResult
Ledger.ingest(observation) -> Receipt
Ledger.post(receipt_id) -> Posted | PendingClassification | Conflict
Reconcile.check(account_id, cut) -> Findings + affected_capabilities
Attempt.close(request_id, evidence_cut) -> Closed | Waiting
Residual.build(closed_attempt_id, pricing_version, request_id) -> Plan | NoChange
```

`Broker.submit` 不能在 quote 缺失等明确未写入错误时一律返回 Unknown。`Ledger.ingest` 返回 received 不等于 posted；`Attempt.close` 返回 Waiting 不等于 crash。

| `v2.3/server/app/services/cash_flow.py` | ingest_facts + post_ledger + allocate_capital | 兼容已有 journal ID；不继续把到账直接等同策略扩资 |
| `v2.3/server/app/services/settlement.py` | observation processor + accounting | 保留订单血缘；替换全批阻断、状态去重遗漏和静默漏记账 |
| `v2.3/server/app/services/reconcile.py` | 统一规范快照和差额案件 | 保留只读核对；退出覆盖真实账本与静默异常过滤路径 |
| `v2.3/live_client` | execution_agent 主干 | 优先复用已冻结包、写前意图和离线执行，不另做第三套客户端 |
| `v2.3/client` | paper broker adapter + 同一 agent | 逐步退掉服务器依赖的提交和另一套终态猜测；不是直接把 live 开关指向 paper |
| `v2.3/server/app/services/shadow_ledger.py` | shadow adapter + 共用估值/账务工具 | 保留无订单能力；虚拟事实单独命名，不导入 broker submit |
| `v2.3/server/app/services/perf.py` | valuation / reporting | 保留查询展示接口；替换资金流收益及缺价按零 |
| Windows PS1 运行与注册脚本 | 稳定 runner + 唤醒配置 | 保留平台接入；业务判断迁到可测试的 application/agent |

迁移中每个账户明确唯一的“正式写入路径”和只读兼容路径。新旧客户端可以短期服务不同账户，但不能在同一账户同时各自掌握完整额度并提交。

## 15. 存储、事务与 API 契约

### 15.1 最小逻辑存储集合

下面是职责，不要求每一项拆成独立库或服务：

| 集合 | 必要键/约束 |
|---|---|
| accounts / strategy_instances | 明确域及物理账户；实例 lifecycle；live 不允许通配账户 |
| observations + processing_status | 来源事件唯一键、载荷 hash、received_at、有效时间、状态与问题；原始事实不可覆盖 |
| journal_headers / journal_lines | 来源/命令幂等键、逐币种借贷平衡、owner、有效时点、correction_of |
| position_lots / balance_projection | 从 journal/成交归属重建；数量、成本、可卖生效日期、book revision |
| targets / rebalances / attempts | instance 直接外键；原始 revision、active plan 指针；不能仅按 account/month 防重 |
| orders / allocations / broker_observations / fills | 稳定意图、broker ID、预定归属、状态历史、成交唯一键与累计覆盖 |
| reservations / grants | 资源身份、金额/数量、唯一持有人、生命周期、原请求及原回执 |
| command_receipts / jobs / outbox | request ID、payload hash、事务结果、重试计划、可查询状态 |
| reconciliations / valuations | 证据 cut、差额分类、质量、版本及修订关系 |
| data_versions / policy_versions | 已批准的输入、代码、交易政策、时点与兼容版本 |

不是给每个 domain event 都建一个新“微服务事件总线”。先保证不可变事实、平衡账务、资源唯一持有和可恢复命令这四种关键记录；衍生查询视图可重建。

### 15.2 四个必须原子的事务

1. **收到事实**：写 observation 与处理任务/outbox 后才返回 durable receipt。无法落盘不能谎称 received；客户端保留原请求待重发。
2. **入账**：验证来源唯一性 → 写分录 → 更新余额/lots 投影及处理水位 → 写后续任务，一次提交。归属不明进入待处理，不能半个 FILLED、半个账本没动。
3. **划拨/发授权**：锁定或条件更新该账户的资源 revision → 检查未承诺余额 → 更新资源与原请求结果，一次提交。并发两次分配不能都读取同一旧余额后各自成功。
4. **发布订单**：先离线计算候选；短事务写完整 target/attempt/orders/allocations、预留及 active 指针。旧批次不删，未发布候选不交给客户端。

数据库事务内不访问 QMT、不跑模型、不等待 HTTP。异步业务通过 outbox 推进；重试使用同一个 request ID 和原始 payload。AWS 的幂等实践同样强调用请求身份区分重试与新的意图；本文据此设计结果重取，而不是“重试前换一个快照再发送”。[幂等 API 实践](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)

### 15.3 拟议 API

```text
POST /vnext/accounts/{id}/observations     # 收事实，返回逐项 receipt
GET  /vnext/receipts/{id}                 # 原结果 + 独立 current_status
GET  /vnext/accounts/{id}/books           # 储备/策略/外部/待认领
POST /vnext/capital-allocations           # 内部划拨命令
POST /vnext/strategy-runs                 # 排队计算，返回 job
GET  /vnext/plans/{id}                    # 完整不可变计划，不按 PENDING 过滤
POST /vnext/grants                       # 在线 preflight/资源授权
POST /vnext/grants/{id}/return            # 交回执行结果与剩余资源
POST /vnext/attempts/{id}/close           # 已有交易收尾
POST /vnext/rebalances/{id}/retry         # 幂等构建 residual
GET  /vnext/accounts/{id}/readiness       # 分能力状态，不是一个万能绿灯
```

路径仅表示边界，可先保留现有路径作兼容适配。cash-flow 旧接口不能悄悄改变为收到即加策略余额；必须有版本和迁移说明。

结构化结果至少包括：`operation_id / outcome / reason_code / scope / durable / receipt_id / next_action`。`READY`、`NO_CHANGE`、`WAITING_BROKER`、`WAITING_DATA`、`WAITING_CASH`、`FAILED` 分开。PowerShell 在原生调用后立即保存退出码，并解析约定字段；不再用 Out-String 后的环境状态或正则文字判断交易是否成功。

### 15.4 SQLite 与未来扩展

初期可保留 SQLite，缩短写事务、单账户命令排序、有限 busy timeout、事务冲突使用幂等重试；连接必须显式关闭。WAL 可在备份/恢复和持久化策略验证后启用以改善读写并发，但它不提供多个同时写者，也不修复资金逻辑。

数据库文件留在本机支持的文件系统，不能把一个 SQLite 放网络盘供多台机器随意写。若以后需要多主机业务 worker、高可用或实际写入排队达不到 SLO，再迁移 PostgreSQL；资金规则与 repository 接口不随数据库改变。[SQLite WAL 说明](https://www.sqlite.org/wal.html)

## 16. 故障隔离、部署与回退

### 16.1 故障处理矩阵

| 故障 | 预期影响 | 恢复 |
|---|---|---|
| Hydra 模型异常/进程 OOM | Hydra 本次计算失败；API、其他策略、已发包继续 | 输入不变的 run 重试或修订 |
| server 停机 | 新目标/新授权暂不可得；已授权离线执行不依赖它 | 本地 outbox 恢复上传，原请求重取 |
| QMT 连接失败 | 该账户不能提交/查询；不误报已成 | 有界重连，仅连接重试 |
| QMT 写调用后 agent 崩溃 | 该意图 Unknown，资源仍占用 | 从券商事实恢复，不重发整批 |
| 一笔成交缺归属 | 该笔待认领；保护相关资源 | 补充映射后一次入账；其他事实继续 |
| API 返回丢失 | server 可能已完成 | 相同请求获得原回执，不新建对象 |
| 报表/企微挂了 | 报告/通知延迟，交易状态不被改写 | 独立作业重试与告警 |
| 整个账户未知资产缺口 | 暂停该账户新风险 | 继续收事实、对账、撤自有单；其他账户继续 |
| 本地 DB 磁盘满 | 不能安全记录新意图，停止新写调用 | 恢复存储并核查券商后续跑 |

健康度分 `process_alive`、`api_storage_ready`、`facts_sync_lag`、`worker_progress`、`account_trade_readiness`。不能因为“某个策略不能下单”就让进程健康检查失败并触发无限重启；数据库不可用也不能只检查目录就报告一切 ready。

### 16.2 发布制度

push 到 GitHub 只是把代码交付，不等于测试通过，也不是生产自动批准。正常顺序：

```text
提交/审阅 → 自动测试 + Windows 契约测试 → 候选 release
→ 数据库副本迁移/恢复演练 → 兼容性核验 → 分账户受控切换 → 验证/观察
```

生产目录只运行完整 release；私有配置、数据、证据、日志和备份在独立路径。严禁在运行目录覆盖几段代码后期待热重载自动拼成兼容版本。

release manifest 记录 server/client/strategy 版本、协议范围、schema 范围、配置政策摘要、迁移 ID 和验收结果。**协议兼容才是必要条件，不是两端 SHA 一样。**

Windows 安装先验证完整候选目录及脚本，再切一个入口指针；任务引用稳定入口。任务切换需要备份完整旧定义，候选失败恢复原定义，不只把某个 legacy task 重新 enable。

### 16.3 为什么要防止错误回退

允许回退兼容的程序 release，但不能把数据库恢复到今天成交之前，然后把旧订单再跑一次。代码回退不撤销真实委托、成交、分红或提款。

恢复旧数据库备份属于灾难恢复：交易写入保持停用，核实旧 grant 和券商事实，补齐缺失事件，确认幂等与资源占用后再恢复。不能只验证服务能启动就放开交易。

迁移采用 expand/contract：先加兼容字段/表和桥接，旧读写退出后再收缩。未知 schema/protocol 的旧版不得接管 live 写入；仍可保留兼容只读诊断。不是“永远不准 rollback”，而是“不能回退真实世界已经发生的历史”。

## 17. 场景验算：从业务结果判断设计是否过度防御

以下金额均为示例，除特别说明不代表当前实际持仓：

| 场景 | 正确结果 | 不能出现 |
|---|---|---|
| Hydra 资本 211,000；账户另外停放 19,000,000 | 储备独立；Hydra 只用自身资本与盈亏 | auto risk 用 19,211,000 当 Hydra 预算 |
| 晚间 grant 已冻结，凌晨储备再到账 1,000,000 | 收到并记储备；原 grant 有效且额度不变 | 要求重做整个 preflight 或给 Hydra 加钱 |
| Hydra 现金 0，卖单预计回款 10,000，但被拒；账户有闲钱 | 买入 WAITING_CASH；不得动用闲钱 | SELL 排在前面就以为资金已实现 |
| 同上，实际只卖得净款 4,000 | 仅可执行已批准且费用也被覆盖的子单 | 按预计 10,000 全部下完 |
| 总账现金 1,000，可用 100、挂单冻结 900 | 可解释冻结；最多处理那 100 的未承诺资源，且核实不被 grant 占用 | 把冻结当消失，退资也拒绝 |
| 300 份委托成 100，余 200 已部撤 | 归属 +100，订单终局，剩余资源释放；server 算 200 residual | PARTIAL 永远等不到“全成/全撤” |
| 九单中一单仍已报 | 八单及该单已知部分可持续入账；冲突补单等待 | 全部回报拒收、手工把已报改废单 |
| A、B 同持 ETF，A 的 lot 今日不可卖，B 可卖 | A 不能借 B 的可卖份额 | 只看 QMT 总可卖就允许 A 卖 |
| 已发给 A 离线额度 10 万，拟把其中 5 万给 B | 先交回/撤销确认；可以处理其他无关空闲资金 | server 超时回收后 A、B 各花一次 |
| server 已成功生成 residual，响应丢失 | 原 request ID 重取原批次 | 失败后换 ID 再建一批，或永久卡在旧状态 |
| 费用暂估 5，交割实际 5.30 | 关联更正 −0.30；归原策略，必要时标记缺口 | 全流程倒回；或忽略费用维持好看的余额 |
| 实际发生人工提款但来源未明 | 记录待认领负差额；限制无法证明安全的新风险 | 因负余额拒绝记录，从此无法对账 |
| 某 shadow 数据缺失 | 该 run 等数据；其他盘和事实 API 继续 | 整个 server 重启 |
| 当月策略合法选择全现金 | 明确 CASH_TARGET，按政策卖出/保留现金 | 与“文件没收到”都返回 NO_ORDERS |
| 公司行动改变份额，昨晚包仍旧数量 | 接收行动事实，限制受影响委托并修订 | 本地随意缩放订单，或让所有策略停摆 |

## 18. 分阶段实施与验收

### 18.1 不做一次性大爆炸切换

| 阶段 | 交付内容 | 退出条件 |
|---|---|---|
| A：契约及现有严重缺口 | 状态语义、事实入口/交易开关解耦、原回执重取、卖款不预支；补回归测试 | 局部恢复场景通过；旧 API 有兼容声明 |
| B：资金核心 | 储备账、归属分录、预留/grant、账户协调、规范快照 | 两策略不能双花；真实入金不被业务闸门拒收 |
| C：旧数据迁移 | 明确期初归属、保留 canary/未决状态、旧 journal 桥接、精确费用差额 | 生产副本迁移可重入；不重复历史退资 |
| D：运行结构 | API/worker 分离、持久工作流、薄 Windows runner、统一结果 | server 重启/任务错过/响应丢失均可恢复 |
| E：模拟盘共核 | 旧 client 接新协议；paper/live 相同状态机，不同适配/权限 | 模拟柜台与 Windows 场景证据齐备 |
| F：影子和报表 | 同估值/费用/行动口径，影子撮合明确、资本流收益校正 | 三盘对照能解释差异而非只比最终 NAV |
| G：受控上线与清理 | 分账户切换、观察、删除旧写路径/历史手填业务 env | 现网证据通过后才退出兼容层 |

每阶段独立可审阅、可验证，不把“迁目录、改算法、迁资金、换任务”塞进一个提交。可以先做不触碰交易写路径的观测和兼容读模型。

### 18.2 迁移特别要求

1. 拍齐 server DB、release manifest、Windows 状态库、旧任务定义及券商期初/未决证据；敏感文件不入 Git。
2. 新账本先从副本和不可变事件重放，用只读差异报告对照旧系统；不是让两套正式写账同时处理同一成交。
3. 为历史没有逐笔证据的持仓建立带证据等级的 opening entries，不编造 broker fill ID。
4. 迁移日未决订单及已下发额度持续占用；旧 writer 停用、状态核实后新 writer 才接管。不能靠批次过期把风险擦掉。
5. 核实现有 Hydra DEPOSIT/DEALLOCATION，作为已有事实迁入，不执行那份旧 handoff 的更正命令第二次。
6. float 转定点产生的舍入差单列迁移调整，不暗改资本；迁移前后现金、证券数量、成本、净入资分别核对。
7. 新版旧版协议兼容窗口和只能只读的版本明确列出；从旧备份恢复不得自动启动 submit。

### 18.3 必须新增的验收组

| 组 | 必须证明 |
|---|---|
| 三盘隔离 | shadow 无真实 broker 调用能力；paper/live 同代码不同凭据、账户和状态；跨域事件被拒 |
| 资本与入金 | 任意 target/未决状态下收可信入金；储备与策略不串；划拨守恒；未初始化也能收账户事实 |
| 并发资源 | 两次并发 allocate、两个 agent、多个策略同证券、server/client 重启，资源不双发/双卖 |
| 卖买依赖 | 卖拒、部分卖、费用超预期、QMT available 延迟更新，不能借其他钱 |
| 状态与归属 | ACTIVE→部成→部撤、重复/乱序回报、累计与逐笔混合、缺 mapping 可补，数量不重记 |
| 传输恢复 | 每个关键事务后/响应前断开；重试返回原 receipt；本地 outbox 跨进程持久 |
| 离线授权 | next-day 无 server；无关入金不失效；已发额度不超时回收；离线急停限制有明确提示 |
| 账务与收益 | 纯入金收益为 0；股息不双计；拆并份额守恒；费用更正；缺价不按零；跨策略费用余数守恒 |
| 日终工作流 | 取消前后崩溃、截止前后逐笔检查、终态延迟、close/retry 响应丢失、错过唤醒可续跑 |
| 故障隔离 | 一个策略异常不阻断 API/其他盘；报表与通知失败不改变交易结果；磁盘满停止新写单 |
| Windows 真环境 | Python/xtquant 版本固定；SQLite 连接关闭、路径/任务 XML/退出码、进程恢复实际验收 |
| 迁移恢复 | 副本迁移两次同结果；旧成交不重复；未决保留；回退代码不回退交易事实 |

采用基于不变量的随机事件序列测试，组合入金/分配/成交/撤单/重复/断网，不只测几个 happy path。资金守恒、数量守恒、无跨账本借用、无重复券商写意图是每一步的断言。

测试层级分别记账：纯函数/mock → 数据库与恢复 → Windows fake gateway → 专用 QMT 模拟账户 → 明确批准的受控 live。没有真实 QMT 的测试不能标成真实端到端通过。

重构验收还要测服务隔离：代表性输入下跑研究任务时，事实接收/查询的延迟与队列积压可观测。具体延迟 SLO 根据部署硬件和测量确定；本轮不编造已经达到的性能数字。

## 19. 已有决定、新设计与待确认政策

**沿用已有决定**：策略只使用划拨资本及自身盈亏；三盘隔离；模型复权/执行原价；Hydra 白名单与限价保护；策略和补单计算放服务器；次日有有效包时离线下单；HTTP 例外不在此次架构重构中重新变成上线阻塞。

**本轮建议确立**：事实与命令分流、真实储备账、平衡分录、资金/证券预留、账户级单 writer、grant 交还、状态分维度、持久工作流、作用域明确的门禁、模块化单体。它们需要实现和验收，不能当成现有系统已经保证。

**实施前需落成版本化业务政策，而非现在猜一个答案**：

- 每个策略的决策/交易节奏、卖款等待到几点、是否批准预拆分买单、补单最长持续周期。
- 经券商确认的下单/撤单/回报窗口与适用品种；手工操作共存规范。
- 实际费用来源及暂估上界、公司行动支付证据、利息及其他账户公共费用的归属。
- 资本增减后何时允许新目标修订；跨策略内部转让是否允许（本建议初版不自动做）。
- 现金差额的绝对精度/暂估范围、等待升级期限、数据陈旧阈值和明确的溢价交易政策。

这些参数不应作为“缺任一项，HTTP 整体不能启动”的条件。没有批准的政策，禁用需要它的新动作；事实接收、已知回报和诊断保持可用。

## 20. 给团队的简要口径

> 我们不是要让每笔操作过更多关，而是把关口放对地方。账户到账要能记下来；给策略分多少钱要明确；已经下过或可能下过的单要防重复。服务器的计算、客户端的执行、日终的记账分别负责自己的事。
>
> 有挂单不代表不能入金，有入金不代表策略可以多花钱。server 暂时不在线不应影响已经准备好的订单，但券商账户和自己的钱仍要在现场核对。单个环节异常，应该能等、能重试、能继续记录事实，而不是整个服务跟着倒下。
>
> 发布要经过测试和兼容核验，因为更新程序不能改变真实世界已经发生的订单和资金。我们可以回退兼容的代码，不能回退已经成交的历史。

最终判断：**目前有必要做边界重构；不能声称现有代码已足够，也不需要为安全把所有动作都绑在一起。** 本规范的目标，是用更少、更明确的规则替代历史叠加的闸门，并把真正的资金约束做实。
