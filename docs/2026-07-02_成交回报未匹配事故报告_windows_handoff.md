## 一、根因时间线（均有服务器日志/数据库佐证）

| 时间 | 事件 |
|---|---|
| 7/1 ~16:04 | Windows 端触发 `POST /admin/run-pipeline?trade_date=20260702` → 生成 18 张 SELL 订单（**批次 A**） |
| 7/1 ~16:05 | Windows 端 `GET /orders?date=20260702` → **拉走批次 A**，写入本地 server_orders |
| 7/1 19:49/19:53 | 服务器部署 SELL offset 修复（e1d37d3），两次重启 |
| 7/1 19:54:32 | 服务器本机再次 `run-pipeline?trade_date=20260702` → **删掉批次 A，生成 18 个新 UUID（批次 B）**，目的是让 offset=0 的新价格生效 |
| 7/1 19:54 之后 | Windows 端**再未拉取过** 20260702 的订单（服务器日志无 GET /orders 记录） |
| 7/2 早盘 | Windows 端按本地缓存的**批次 A** 下单，QMT 全部成交 ✅ |
| 7/2 ~15:44 | 收盘推送成交（批次 A 的 ID）→ 服务器只有批次 B → **18/18 未匹配**，成交一条都没入账 |

机制一句话：**order_id 是随机 UUID，管线每重算一次就整批换新；客户端拉走信号之后服务器再重算，客户端手里的就是废 ID。**

同模式旧案：6/30 晚，20260701 批次被拉走（10 条）后，另一处又重算了一次（变成 28 条新 ID）→ 7/1 的成交也全部未匹配。7/1 16:00 cron 日志里 `preserved_settled: 0` 就是证据（该日没有任何订单被结算过）。

## 四、防再发（已实现，本次一并部署/合入）

**服务端**（已上线）：
1. `orders.fetched_at`：`GET /orders` 拉取即盖章。
2. **重算护栏**：某日订单已被客户端拉取 → `run-pipeline` 默认拒绝重算（返回 `skipped: already_fetched`）。确需重算必须 `force=true`，并且**操作者有义务通知 Windows 端重新拉取信号**。已结算护栏（该日已有成交入账 → 拒绝重算）不受 force 影响，任何情况不可绕过。
3. **未匹配候选提示**：成交回报 unmatched 时，服务器按 (日期, symbol, 方向, 数量) 返回疑似同单的候选 order_id（`unmatched_candidates`），以后再出这类事故不用靠猜。

**客户端**（本次 git pull 拿到，请部署替换）：
4. `order_submit.py` **下单前强制核对批次**：每天早上下单前重新 `GET /orders`，发现本地批次与服务器不一致 → 自动用服务器最新批次替换后再下单，并微信报警提示。这一条从客户端侧把整类事故杀死。
5. `trade_result.py` 推送带上 symbol/direction，配合服务端候选提示。

**操作纪律（双方共同遵守）**：
> **任何时候在服务器上重算了未来交易日的管线（force），必须通知 Windows 端在下单前重新拉取信号。** 反过来，Windows 端如果早上看到「批次已过期，已用服务器最新批次替换」的报警，属于护栏正常工作，不用慌，但请知会服务器端确认前一晚发生过什么。

## 五、FAQ

**Q：为什么 QMT 全成交了还报「未匹配」？**
成交是真的，只是服务器对不上号——它手里的订单 ID 已经不是你下单用的那批了。钱和股票都没问题，问题只在服务器的记账。

**Q：重推会不会重复入账？**
不会。服务器有幂等守卫（order_id+时间+数量+价格），且批次 B 此前从未入过账。

**Q：以后还需要每天盯这个吗？**
护栏部署后：服务器默认拒绝重算已拉取批次；客户端下单前自动核对。两道防线都要突破才可能复发。如果再看到「未匹配」报警，响应级别按 P0 处理（意味着有成交没入账），服务器返回里会直接带候选映射。
