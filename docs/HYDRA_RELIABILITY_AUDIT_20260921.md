## 1. V5.3：不能把“网络问题”直接等同“订单没有提交”

只读数据库事实：

- `paper_v53_v53` 持仓账本最后更新于 2026-08-03。
- 有效日期为 20260901 的九笔订单全部 `EXPIRED`，**九笔都有 fetched_at**。
- 本次查询范围内未见后续 V5.3 九月订单；实例没有保存月度 target 的 strategy_state。

`fetched_at` 证明服务器已处理过取单，但不证明 Windows 完整收到，也不证明成交。服务器时间到期的 EXPIRED 不是券商的零成交证明。故障发生在取单、提交、回传中的哪一段，仍需 Windows 记录定位。

原实现只在月初生成目标，没有保存可持续追踪的目标份额；单次 GET 失败还可能告警后以成功退出码结束。因此一次中断可能失去整个月的恢复机会。这是已查明的恢复设计缺口，**不是已查明九月事件一定由 GET 超时造成**。

本地修复：

1. 模拟盘 `client/order_query.py` 对连接错误、超时、HTTP 429/502/503/504 最多尝试三次，间隔 1、2 秒。失败耗尽以非零退出码结束。业务错误与身份认证错误不当作网络抖动重试；不新增 QMT 下单重试。
2. V53 保存本月目标份额、原始权重与生成日期。月内恢复使用“已冻结目标份额 − 已确认持仓”，不每日重新计算权重追涨杀跌。部分成交只补剩余差额；缺价格时不能误标 COMPLETE。
3. 已取走的旧委托需有终局回报、账本无差异且无待对账状态才允许差额续做。这个限制只影响 V53 的续做，不新增阻塞其他策略、入金或整个服务的总闸门。

九月恢复顺序：先导出九筆 order_id 对应的本地取单、order_submit、trade_result 日志及 QMT 最终委托 / 成交；确认已成交数量已入账，再恢复获批九月目标，生成新的日期有效差额单。**不要直接将旧 EXPIRED 改回 PENDING，也不要按九笔全未成交重发。** 当前补丁面向新保存的月度目标，不能自动猜出旧实例缺失的九月目标。

Windows 需同时交付 `client/order_query.py` 与其新依赖 `live_client/network_retry.py`；此处共享文件名不代表改动了实盘 LiveServerClient 或离线 submit。

## 2. 分红：是净值与现金两个时点，不是给策略提前发钱

511260 本次分红：登记日 9/17、除息日 9/18、场内现金发放日 9/23，每份 1.2747 元；不能误用场外发放日 9/21。[上交所分红公告](https://www.sse.com.cn/disclosure/fund/announcement/c/new/2026-09-15/511260_20260915_8V2W.pdf)

旧估值仅有“现金 + 未复权持仓市值”，除息价格下降时漏掉应收股息，会制造账面假跌。此次本地会计链为：

- 按登记日持仓确认权利；登记日后卖出不抹掉权利。
- 除息日计入应收股息，增加 NAV，**不增加可交易现金**。
- 实际分红现金事件入账后，同一权利退出应收，避免收入计算两次。计划支付日期本身不触发现金入账。
- 同账户不同策略持有同一 ETF，权利按实例分别记录；真实到账仍通过既有现金 / 收益分配通道处理。
- 每次 NAV 同事务保存现金及应收组成；风险报表不再从含应收的 NAV 错推可用现金。分红属于投资收益，不从组合回报中按外部增资扣掉。
- 历史快照没有组成记录时维持旧解释；登记权利本身不会偷偷重写过去 NAV。

部署新增两张表 `dividend_entitlements`、`perf_valuations`，通过现有 `init_db/create_all` 建表，不改旧表列，不删除历史记录。需先备份 / 在数据库副本验证迁移，再单独批准上线。

登记工具（默认仅预览）：

```sh
cd v2.3/server
venv/bin/python -m scripts.register_dividend_entitlement APPROVED_MANIFEST.json
```

清单字段由 `DividendRequest` 定义：执行域、账户别名、实例、证券、登记 / 除息 / 支付日期、登记日归属份额、每份分红、证据 SHA-256、将要匹配的现金来源及事件 ID。批准后才可使用 `--apply`。不得填入私密清单到 Git。

部署限制：现金匹配目前要求明确的一笔同实例 DIVIDEND/CNY 事件及准确金额；不能用余额变动猜测。账户级批量到账应先经现有收益分配产生策略级事件，再引用其准确身份。部分到账、税差、错误登记更正与拆分支付尚需专门处理，不能宣称完整企业行动自动化已完成。

历史净值必须从历史持仓 / 现金逐日重放，不能用今天持仓调用旧日期 snapshot_all 冒充重算。本轮只验证了会计算法和既有 9/18 分红差异，不写回生产历史曲线。

## 4. V48 为什么跌：五日资产共跌，而不是“防守就不许亏”

使用已有冻结文件与研究版本重新计算，九个目标权重与获批 9/3 目标误差小于 1e-10。比较窗口为 **9/8 收盘至 9/15 收盘**，对应既有真实持仓重建约 −0.4416%；这不是 9/21 最新五日收益。

匹配方法：九资产五日收益按各自历史五日波动标准化，比较向量距离；候选限于 2025 年及以前，各入选窗口互不重叠。历史组合收益采用当时模型持仓，不用今天权重冒充历史回测。

| 类似资产表现区间 | 模型五日回报 | 主要共性 |
|---|---:|---|
| 2021-06-09 → 06-17 | −0.7143% | 沪深300、黄金、豆粕与债券一起跌 |
| 2024-05-23 → 05-30 | −0.1635% | 沪深300、黄金、豆粕跌，债券小幅上涨 |
| 2024-01-11 → 01-18 | −0.1129% | 同样存在股票 / 黄金 / 豆粕同步负收益 |
| 2024-12-12 → 12-19 | −0.4038% | 债券收益不足抵消股票 / 黄金 / 豆粕损失 |

本次窗口的主要负贡献来自豆粕、沪深300和黄金；十年债实际是小幅正贡献。尚无证据可以把这段下跌归因于旧远期利率信号。分红造成的 9/18 假跌是另一件事，不能拿它解释 9/15 以前的损失。

1632 个历史五日窗口中，149 个模型回报不高于这次重建回报。它们互有重叠、资金与执行口径不同，不能把 149/1632 当作独立事件概率。相似窗口是事后描述，不证明反弹将发生，也不能代替回测与实盘滑点复核。

## 5. 713 base 审计：测试绿，不等于回测与部署等价

本次读取的部署研究源为 **88c2cb1 + ROE PIT null 修补发布**。服务器 relay 与研究生产器分别审查；研究端未作修改。

已复现：

1. **新日期包着旧子组合。** 正式目标外层 `as_of_date=20260831`、`decision_date=20260907`、T1_5050，内层 Hydra 权重仍是 20260630。`load_hydra_weights` 只拒绝未来数据，所以此组合被接受。应绑定同一决策月的子组合 / 明确沿用政策，不能只检查外层日期。
2. **缺失收益按零处理。** `monthly_hydra_return` 对空月份返回 0.0；缺部分交易日也没有完整性校验。复盘时应标记数据不完整，而不是当作真实持平。
3. **组合切换漏计换仓。** 固定同一 TOP50 名单、从 TOP50 切换为 T1_5050 的最小复现中，两期 cost 都为 0；代码只按 TOP50 名单变化估成本，没有覆盖完整子组合切换。不能直接拿这条曲线证明实际策略回报。

另外，研究回测在持仓价格缺失时对剩余证券重新归一化；是否允许这种假设，以及它对退市 / 停牌样本的影响，需要完整数据复核。

原生产器五项测试通过，但其中名为“使用可交易 Hydra 权重”的测试实际强制 TOP50 分支，未走当前生产的 T1_5050 / AUX_HYDRA 关键分支。这解释了为什么已有测试没暴露上述问题。服务器 relay 测试不能替代研究端的经济口径测试。

未完成：完整 PIT 回测重跑、目标份额 / 实际手续费 / 子组合内部交易成本对齐，以及小市值研究源 GitHub 仓库身份的完整确认。因此本轮结论是**发现不一致，暂不能认定 713 base 等价**，不是迁移放行意见。
