## 2. 设计原则（业界做法 + 本项目教训）

1. **订单号由服务器生成，生成后永不更换**。订单号写进委托备注，长度 ≤20 字符。重算只会新增订单，不会给旧单改名。参考 FIX ClOrdID、Alpaca `client_order_id`、vn.py QMT 网关。
2. **先记日志，再下单**。代理在调用 `order_stock` 之前，先在本地写入"提交中"；下单结果不明的单，在拿到券商证据之前绝不重发（参考 Hummingbot、Binance）。
3. **持仓、现金、委托、成交都以券商为准**。本地只记录"意图"和"归属哪个策略"。对账发现不一致就暂停，不自动"修正"实盘（参考 NautilusTrader、LEAN）。
4. **订单状态只有一个写入者**。所有状态变更都先写成只追加的事件，当前状态由事件推出来；非法的状态转移直接拒绝。
5. **成交是事实**。任何状态下都接受晚到的成交；以（账户，券商成交编号）去重；匹配不上的成交记为"外部成交"，绝不丢弃。
6. **新目标和补单彻底分开**。新的目标版本覆盖旧的；补单是同一个版本重新计算差额，差额不能超过原目标（参考 LEAN 的目标集合、vn.py 的组合策略）。
7. **计划器是纯函数，回测和实盘调用同一份代码**。每轮结束后，生成实际执行和回测预期的对比报告。
8. **按交易所规则做事前检查**：100 份整手；0.001 最小价位；卖出数量不超过可卖数量（T+1）；14:57–15:00 和 9:20–9:25 不能撤单（上交所 2026 规则第 3.3.1 条）。

## 4. 目标架构

### 4.1 组件与边界

```
            ┌──────────── 服务器（单写者）────────────────────────────┐
 研究/月度 → │ TargetStore   目标版本（不可变，有版本号）               │
            │ CycleService  调仓周期的生命周期：开 → 时段 → 关          │
            │ Planner       纯函数：周期 + 对账快照 + 行情 → 时段计划    │ ← 回测导入同一模块
            │ OrderLedger   订单意图 / 事件 / 成交；状态机唯一写入点      │
            │ Reconciler    券商快照 ↔ 账本；对不上就暂停                │
            │ Projection    成交 → 策略账本 / 净值 / 看板（只读派生）     │
            │ API /oms/*    取计划、传事件、传快照、查状态               │
            └────────▲──────────────────────────┬───────────────────────┘
                     │ 事件 / 快照（幂等）         │ 已签名的时段计划
            ┌────────┴──────────────────────────▼───────────────────────┐
            │ Windows 执行代理（薄）：账户锁、本地日志、QMT 网关          │
            │ 时段任务：开盘前对账 → 卖出 / 买入 → 14:55 撤单 → 日终快照   │
            └────────────────────────────────────────────────────────────┘
```

- **TargetStore**：月度研究产出一个目标版本，内容包括权重、信号日、来源哈希。新版本激活后，旧版本标记为被覆盖。
- **CycleService**：一个目标版本对应一个调仓周期。开周期时冻结：整手目标股数、锚定价、规则参数、信号日净值、整手误差。周期按时段推进；关闭原因只有三种：完成、窗口到期留有剩余、被新目标覆盖。关闭时生成执行报告。
- **Planner**：输入周期、对账后的券商快照和最新行情，输出一个交易时段的订单意图。它不读写数据库，也不访问网络。回测的 `policy_replay.py` 改为导入这个模块，并用"同一输入得到同一订单"的金样本测试锁定口径。
- **OrderLedger**：唯一能写订单状态的地方。
- **Reconciler**：对比券商快照和账本，结果为通过或暂停。
- **Projection**：把成交派生成现有的 `instance_state`（按策略归属的账本）、净值和看板，现有页面无需改动。
- **执行代理**：由现有 `live_client` 收缩改造而来。复用 `gateway.py` 的 QMT 封装、`state.py` 的本地日志和账户锁。删掉它本地的资金规划逻辑：预算和股数全部由服务器计划给出，代理只做"券商可用现金是否够"的最后检查。

### 4.3 订单状态机

```
PLANNED → RELEASED（代理已取） → SUBMITTING（已记日志、调用中）
   SUBMITTING → ACKED（券商单号 > 0） | REJECTED（-1 且券商清单里有废单 57）
   SUBMITTING → UNKNOWN（超时/异常/状态 48、49、255 持续超过 60 秒）
   UNKNOWN → 按备注查到券商单 → 并回对应状态；日终券商当日委托里没有 → NOT_SUBMITTED
   ACKED/PARTIAL → PARTIAL（55） → FILLED（56）
   ACKED/PARTIAL → PENDING_CANCEL（51/52，非终态） → CANCELLED（53/54，保留已成交数量）
   ACKED → EXPIRED_DAY（15:00 后状态 50 且已无挂单，附券商证据）
终态：FILLED、CANCELLED、REJECTED、EXPIRED_DAY、NOT_SUBMITTED
```

- **收盘后的终态判定**：A 股普通限价单当日有效，15:00 后交易所自动作废未成交的部分。但 QMT 不会把状态改成"已撤"。9/4 那 3 笔单收盘后一直显示 50（已报），旧代码一直在等一个永远不会来的终态，整批结算被卡死。新规则：15:05 日终查询时，如果状态仍是 50 或 55，就终结为 EXPIRED_DAY；已成交数量以当日成交明细为准（按 `traded_id` 去重），委托里的 `traded_volume` 只做核对。
- 晚到的成交在任何状态下都直接记入 `oms_fills`，并更新成交数量；如果已经是终态，标记为"终态后成交"，交给对账处理。
- 订单进入终态后，只能通过有券商证据的更正事件改动。
- UNKNOWN 永远不会自动重发。

### 4.4 两阶段时段流程（北京时间）

**卖出日 S（参考日）**

| 时间 | 代理 | 服务器 |
|---|---|---|
| 14:45 | 连接 QMT，做开盘前对账快照（PRE），上传；取卖出计划，或使用前一晚缓存、带签名的计划 | 对账；不通过就把时段设为 HOLD 并发微信告警 |
| 14:55 | 撤掉本账户本周期还在挂的买单（多时段窗口的第 2 天及以后才会有），等到终态 | — |
| 14:57:05 | 把卖单报入收盘集合竞价；失败就重试到 14:59:00，过了就记 NOT_SUBMITTED | — |
| 15:05 | 日终快照（EOD）：委托、成交、持仓、现金；上传事件 | 终结卖单 → 对账 → 用券商现金生成 S+1 的买入计划 |
| 15:20 / 18:00 | 拉取并缓存 S+1 的计划（两次，保证冗余） | — |

**买入日 B（S 的下一个自然日）**

| 时间 | 代理 | 服务器 |
|---|---|---|
| 09:00 | 开盘前快照，核对缓存计划的哈希和持仓 | 对账 |
| 09:15:05 | 把买单报入开盘集合竞价（9:20 前还可以撤） | — |
| 09:30–14:55 | 每 30 秒查询一次（另外订阅回调作为补充），上传状态和成交事件 | 更新账本 |
| 14:55 | 撤掉没成交的部分，等到终态（14:57 之后不能撤） | — |
| 15:05 | 日终快照 | 终结买单 → 对账 → 周期结束则关闭；否则生成下一个卖出时段的计划 |

服务器只在收到快照时触发规划，不再依赖一串定时任务环环相扣。服务器挂了的时候，代理用缓存的计划照常执行，恢复后补传事件。

**日内轮询不参与下单决策。** S 日卖出，S+1 日买入，买入预算来自 S 日终快照，而不是日内"看到卖单成交再下买单"。30 秒轮询只用来更新状态和上传事件。这正是两阶段方案可以用日线回测的原因：两条腿都在集合竞价成交，日线的开盘价和收盘价就是官方竞价成交价。盘中挂单的影响已经用上下界检验过：只在开盘竞价成交的保守版本，和盘中触到限价就成交的乐观版本，近期都是年化拖累 0.275、0/22 轮超标。

#### 4.4.1 跨天成交怎么判定

A 股委托只在当天有效，所以不存在"昨天的单今天成交"。所谓跨天，其实只有两种情况：
- 当天成交了，但当天没拿到回报；
- 当天没成交，下一个时段要补。

判定分三层：

1. **主依据：S 日 15:05 的日终快照**，包括当日委托、当日成交、持仓、现金。QMT 的委托和成交查询只返回当天的记录（10/7 演练时核实），所以日终快照必须当天完成：15:05 取第一次，15:30 再取一次确认，两次不一致就以后一次为准，并记录差异。
2. **决策依据：持仓，而不是订单状态。** 下一时段的计划只看"冻结目标股数 − 券商实际持仓"。早上开盘前，前一天的委托已经全部失效，不会有在途单。因此即使某笔回报丢了，只要持仓是对的，就不会重复买；订单状态只用于审计和策略归属。
3. **兜底：日终快照缺失时（代理宕机、QMT 断开），按持仓变化归因。** 次日开盘前快照的持仓变化，如果能被 S 日的订单完整解释（同一标的、同一方向、数量不超过剩余量），就自动记为成交：证据类型是"持仓变化"，现金以券商为准，价格等交割单核对后补记。解释不了就暂停，转人工处理。

另外加两道防线，防止晚到的成交导致超买：
- **09:00 重算**：开盘前快照和生成计划时用的快照不一致（持仓或现金变了），服务器就用同一个计划器重算，生成新的计划哈希；代理取新计划。
- **代理逐笔上限**：代理每下一笔买单之前，用券商实时持仓核对"持仓 + 本单数量 ≤ 冻结目标股数"，超了就缩量。即使服务器不可达、只能用缓存的计划，这道检查也不依赖服务器。

回测里与之对应的是"回报晚一天"情景。C3 近期年化拖累：乐观 0.275、保守 0.356；欠配 2/22 轮超过 2%，原因是少了一次补单机会。这说明日终快照的可靠性直接影响执行质量，所以第 8 节把它列为必测项。

### 4.5 对账闸门

- **开盘前（PRE）**，以下任一条不满足就暂停（HOLD）：
  - 本策略归属的每个标的，券商持仓 = 账本持仓（各策略账本加总后对比）；
  - 没有未知的挂单；
  - 本策略现金 ≤ 券商可用现金。
- **日终（EOD）**：
  - 本时段每一笔意图都必须进入终态；UNKNOWN 必须已用券商当日委托清单解决；
  - 每一笔券商成交都匹配到意图，或者明确记为外部成交；
  - 持仓 = 上一次持仓 + 本时段成交。
- **暂停后**：不出下一份计划，发告警。必须经过人工处理接口才能放行，处理时要写明原因，全程留痕。实盘不做自动修正。

### 4.6 新目标与旧周期

新目标版本到达时：
1. 冻结旧周期，不再出新计划；
2. 确认旧意图全部进入终态，必要时先撤单；
3. 旧周期以"被新目标覆盖"关闭，并出报告；
4. 新周期以券商实际持仓为基础重算完整差额。

旧周期没收口之前，不会开新周期。

### 4.7 资金与多策略共享账户

- 账户里约 1900 万元不属于 Hydra。
- Hydra 的现金 = 初始拨款 + 资金变动 + 本策略成交净额 − 实际费用，由 `oms_fills` 推出来。
- 买入预算 = min（Hydra 现金，券商可用现金 − 在途买单冻结）。
- 手续费以券商成交回报为准；没有回报时先按估算记账，到日终再校正。

### 4.8 失败处理

| 场景 | 处理 |
|---|---|
| 服务器不可达 | 代理用缓存的签名计划执行；事件留在本地，之后补传；不在本地重新规划 |
| QMT 断线 | 重新连接（每次连接只用一次，用新的 session_id），重连后做一次 ADHOC 快照对账，再继续 |
| 下单超时或返回 -1 | 置为 UNKNOWN，按备注查询，查不到就等日终委托清单，绝不重发 |
| 部分成交 | 14:55 撤掉剩余部分，等到终态；剩余部分进入下一个时段，只补原差额 |
| 废单（57） | 记录原因；当天不重试；如果是规则问题，例如价格笼子、可卖数量，下一个时段修正后再出单 |
| 停牌、零成交量 | 计划器跳过，并记"停牌"原因 |
| 资金不足 | 计划器按资金分配（优先级、同级按剩余金额比例、余量按整手补齐），记"资金不足"原因 |
| 晚到成交 | 直接入账；如果订单已是终态，标记后交给对账；下一份计划自动基于最新持仓 |
| 日终快照缺失 | 次日开盘前快照按持仓变化归因（见 4.4.1）；解释不了就暂停；在此之前，代理逐笔上限检查照常生效 |
| 收盘后仍显示 50/55 | 15:05 终结为 EXPIRED_DAY，已成交数量以成交明细为准（9/4 的教训） |
| 对账不一致 | 暂停，告警，人工处理 |
