## 1. 这次部署的业务目的

让已经批准的 Hydra 目标在合格日期、以新的原价形成订单；未成交只补实际差额；卖款没有到位时买单等待；早上下单不依赖服务器在线。不是另加一套审批，也不是放宽价格追单。

需求来源：同伴的《HYDRA_EXECUTION_POLICY_EXPERIMENTS_AND_DECISION_20260909.md》最终决策。本次实施当前方案，**不实施下一阶段候选参数**。文中回测统计未在本轮独立复算，不能把本轮软件测试当作收益验证。

| 业务要求 | 本次代码行为 |
| --- | --- |
| 相邻自然日且两天都是交易日 | live Hydra 使用冻结日历验证；周五原价不能直接生成周一执行包 |
| 全体买卖最多 50bp | 保持服务器限价上限；政策随批次内容绑定；不启用 100/150/200bp |
| 日期不合格 | 保存原始获批请求为等待计划，正常返回 `WAITING_EXECUTION_DATE`，不创建委托 |
| 等到合格参考日 | 使用当日新不复权行情、最新归属现金和持仓；不是从历史目录任挑一个文件 |
| 初次等待与 residual 的区别 | 初次等待保留已批权重，到执行准备时计算份额；已有 rebalance 的补单保持 target_shares 不变，只算实际差额 |
| 完成了就不要补 | 只有最新 attempt 为 `RESIDUAL` 才生成新的补单；`COMPLETE` 不补；同次调用重放不重复建单 |
| 先卖后买 | 本地先发原批次卖单，再按确认卖款和实际可用现金检查买单；不改价、不拆量、不复制委托 |
| 资金到账晚一点 | `DEFERRED_CASH` 是尚未调用券商的本地事实；每 30 秒恢复一次，14:55 停止新调用 |
| 下单结果不确定 | 不自动重试该交易调用；保留未知意图并查明，避免重复下单 |
| 15:00 后还是已报 | 保留 9 月 9 日批准的当前券商 raw-50 到期规则；原始 50 不改成假 57，累计成交仍入账 |
| 1900 万暂存在同一账户 | 不把全部账户余额分给 Hydra；归属模式下额外未分配现金本身不阻断执行，订单仍按 Hydra 子账本额度计算 |

月初碰到周末的例子：周五产生已批目标 → 保存等待计划 → 周一收盘发布新原价 → 周一晚按原权重和本策略现金/持仓生成并冻结 → 周二 09:10 离线提交。不是用周五价格买周一，也不是等候过程中每天重新跑一遍选股。

## 2. 正式日程建议（本轮仅提供脚本，尚未注册）

所有下面的时间都是中国时间。**Windows 任务计划的机器时区必须是 China Standard Time，并核对系统时间同步。** Python 的执行窗口使用 UTC+08:00；任务计划本身仍按机器时区运行，安装不会替同伴修改操作系统时区。

| 时间 | 任务/阶段 | 实际职责 |
| --- | --- | --- |
| 下一合格执行日 09:10 | 一次性 Submit → `submit-queue` | 只读昨晚冻结批次及 PASS 回执，连接本地 QMT；卖出先发，买单等实际资金；不访问 server |
| 09:10–14:55 | 同一个受限队列进程 | 仅在 `WAITING_FOR_CASH` 时每 30 秒继续已知未发送订单；每次释放账户锁；未知交易错误终止 |
| 14:55 | CancelOpen | 保留原撤单请求阶段；发请求不等于已撤。队列逐笔调用前也检查 14:55 截止；已经在途的调用不伪称可强行撤回 |
| 15:00 | 委托有效期边界 | 当日适用 Hydra raw-50 剩余量按政策到期；不把其他账户、品种或不明订单强行套用 |
| 15:10 | SettleClose | 先回传独立可核实成交，再核对账户/归属账并 close；失败可由任务计划 5 分钟后重试一次，不是重试下单 |
| 15:30 | ExecutionData | 读取 QMT 当日 `dividend_type=none` 日线和日历，发布到 server 的不可变执行数据仓库 |
| 15:30 | MarketBackup（原任务） | 原诊断行情备份保留；不是新的执行数据入口，两者回执不可混用 |
| 16:00 | Retry → `advance` | 重新发布/确认当日执行数据、重观测 settle-close，再让 server 恢复等待计划或计算 residual |
| 18:00 | QueryPreflight | 再检查行情与 close/advance，正常后 query → preflight → 注册下一合格执行日一次性 09:10 任务 |

16:00/18:00 的重新发布是幂等数据事实，补发 15:30 遗漏不生成第二份同内容数据。当天已经生成并冻结的 attempt **不会因 18:00 出现修订行情而静默重新定价**。假日返回正常跳过；跨周末返回正常等待，不要求人工反复开闸。

09:10 一次性任务运行时限由 15 分钟改为 360 分钟，以容纳等待现金；没有设置自动重试下单，也没有追赶错过的交易任务。业务循环在 14:55 截止，不会因为任务时限更长而继续交易。

## 3. Server 和 Windows 的边界

新增 server 入口沿用现有 live Bearer token 的域/账户权限：

- `POST /hydra/execution/data`：仅发布不复权日线及交易日历。不修改资金、权重、订单，不要求开启新订单开关。
- `POST /hydra/execution/advance`：按已批计划或已结案 residual 推进执行。需要该策略/账户身份、当前账户快照及证据 SHA；不接受 Windows 自算的 orders、限价或 residual。

`/hydra/targets/stage` 与 `/hydra/rebalances/retry` 现在还可能正常返回等待结果。调用方应读取 `data.status`：等待计划并非失败的订单，更不是已经生成可下的单。初始计划回执的 `plan_id` 要保留；同请求重复发送不会再建计划。

新自动流程的 `advance` 从 server 取得待办身份和已发布执行数据，**不再要求每天手填 `HYDRA_LIVE_RETRY_*` 三元组**。旧手动 `retry` CLI 仍保留且仍要求其原绑定；旧私有配置如保留这些字段须保持完整合法，也可以在获批迁移时一起清除三个字段。不要把旧手动命令重新接回 16:00 任务。

新表为 `hydra_execution_plans` 与 `hydra_execution_publications`，通过原模型初始化创建。原研究四流及其哈希保留；执行刷新另记 raw/calendar 哈希。原价数据与 manifest 以完整目录原子发布，避免写到一半使后续一直失败；并发发布相同内容只保留一份。

执行政策存入 attempt 的 risk_snapshot，并参与 batch SHA；拉单 API 的每笔订单增加 `execution_policy`。客户端会核对新政策及批次内容。旧批次不带该字段仍可读取，**这是兼容能力，不代表旧包自动符合新日期政策**。

## 4. 哪些等待正常，哪些需要处理

| 结果 | 含义及处理 |
| --- | --- |
| `WAITING_EXECUTION_DATE` | 正常日历等待；原权重/目标留存，下个合格参考日晚继续 |
| `WAITING_EXECUTION_DATA` | 当日原价或日历尚未发布；补发布后再 advance，不沿用旧价 |
| `WAITING_FOR_CASH` | 尚未发给 QMT 的买单等实际资金；自动队列恢复，收尾时仍不足的本地未发送量交 server 后续算差额 |
| `WAITING_FOR_BROKER` | 有订单身份/结果未能独立确定；已确认的成交照常回传，只暂停本轮 close/新补单 |
| `WAITING_RECONCILIATION` | 真实持仓或归属账未对齐，或迟到成交影响了旧包；先登记真实事实与核实旧包，不自动归属人工买入 |
| `NO_PENDING_EXECUTION` / `NO_ORDERS` | 没有需要生成/拉取的单，不建立空的 09:10 任务 |

18:00 收到等待结果时不继续拉旧批次或注册新提交任务；缺数据/对账问题会提示处理，日期等待是普通通知。**它不会远程撤销以前已经注册且冻结的离线任务。** 若发生迟到成交、人工补齐或策略切换，须在 Windows 明确核实旧包和旧任务，不能指望早上联系服务器来拦住旧包。

同伴文中称 9 月 8 日人工补齐 `513100 × 1000`、`513500 × 1200`、`518880 × 800`。本轮未访问券商验证。上线前请用真实成交/交割证据入账并检查实际持仓；不能把这三行文字当作成交回报，也不能无条件重发原 residual。

## 5. 和资金子账本迁移一起交接

继续使用 [策略增减资与迁移说明](STRATEGY_CAPITAL_MOVEMENTS_MIGRATION_20260908.md)。本次不会重新初始化账户，也不会把余额改成某个固定数。

- 账户入金事实先记录；指定给 Hydra 的资本通过增资/减资分录调整。
- 本策略额度随本策略盈亏变化；其他策略与暂存现金不是它的收益。
- 已冻结的离线包不会被事后增资自动改量。增减资发生在冻结之后时，影响下一份获批未冻结目标；若要改变当前目标，先完成旧包生命周期，再显式变更，不能只改一个余额文件。
- residual 继续跟随原 target_shares，不会借“补单”把新增资金全部加进去。
- 先卖后买不代表减资时自动卖资产。当前现金不足以减资时，卖出筹资仍需要明确的目标/交易安排。
- 真实滑点记录和容量评估沿用第一阶段功能；本次没有凭少量样本自动推荐增资金额，也没有开启差异化限价。
