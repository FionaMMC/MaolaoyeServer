## 1. 这次改什么：不再等一个不会回来的“废单回报”

用户明确了当前链路的实际情况及采用的规则：QMT 订单可能一直显示“已报”（原始状态 50），不会因为未成交而自动变成“废单”（57）。对于本次纳入的 live 域 Hydra 当日订单，**到中国时间 15:00 后仍为 50，应按本轮有效期已结束处理**。模拟盘和非 Hydra 委托不自动套用这条政策。

因此，不能继续采用“只关工作流，但只要还是 50 就永久不准结案、永久不准补单”的方案。正常收盘路径应当能够结束旧单，按实际持仓计算差额，生成下一次需要的补单。

同时，系统不把原始 50 改写成“券商已经报 57”。准确的记录是：

> 券商原始状态仍为 50；按照这笔委托适用的 15:00 政策，本轮剩余未成交数量已到期。

这不是新增一个等待人工开闸的审批流程。政策已经由用户明确；时间和订单身份匹配后由程序执行。它也不是声称所有券商、所有品种、所有委托类型都遵循同一规则。

## 2. 最小业务合同

| 观察到的情况 | 本轮处理 | 是否继续等待 57 |
| --- | --- | --- |
| 当日 15:00 前，原始状态 50 | 尚在有效期，保留待处理状态 | 不提前作废 |
| 当日 15:00 及以后，匹配到本地冻结 Hydra 订单，原始状态 50 | `EXPIRED_BY_POLICY`；保留已经成交的数量与价格，仅剩余部分到期 | 不需要 |
| 券商已明确全成、已撤、部撤或废单 | 按实际券商终态及累计成交记录处理 | 不需要 |
| 订单没查到、账户/标的/方向/数量/身份不符 | 只标记该笔待核实，不编造到期证明 | 不是“必须等 57”，而是还没认清这笔订单 |
| 其他原始状态或其他交易日的缓存 | 不套用本条 raw-50 政策 | 依其真实事实/适用规则处理 |

时间使用中国 UTC+08:00 的交易日和 15:00 边界，不使用服务器或 Windows 所在机器的默认时区。执行端在本轮收尾时停止该本地冻结批次继续发新单，再上传观察；关闭本地执行不需要先证明 server 活着。到期时可证明从未调用 QMT 的本地订单记为 `NOT_SUBMITTED / EXECUTION_WINDOW_EXPIRED`，不伪造券商废单；已进入调用但结果不确定的订单仍单独核实。

`EXPIRED_BY_POLICY` 是有效执行状态，不是撤单 API 的返回值，也不表示程序执行了撤单。已有的盘前/收盘前撤单操作保持独立。

## 3. 保存哪些证据，避免日后说不清

到期观察在正常成交回报字段之外包含：

```json
{
  "status": "EXPIRED_BY_POLICY",
  "raw_qmt_status": 50,
  "status_observed_at": "2026-09-09T15:05:00+08:00",
  "expiration_policy_id": "QMT_DAY_ORDER_1500_V1"
}
```

同时携带原有的内部订单 ID、匹配的 QMT 委托号、累计成交数量和真实累计成交均价。示例只展示新增字段，不能作为完整回报直接提交。

政策 ID 说明采用哪条经营规则，**不要求 server/client 的 Git SHA 一样，也不需要每次运行重新批准**。原始观察与政策解释分开留存；不能为了通流程把原始 50 改成 57，或抹掉之后收到的新成交。

Close 回执也分开表达两个事实：

- `effective_finalized: true`：本轮所有相关订单在适用执行规则下可以结案，包括政策到期。
- `broker_finalized: false`：至少有订单是按政策到期，而非收到券商明确终态；不是 Close 失败。
- `status: COMPLETE`：按实际持仓已达到目标，不补单。
- `status: RESIDUAL` 且 `retry_ready: true`：存在实际差额，可以进入下一次补单流程。

不能再用 `broker_finalized == false` 单独阻挡符合本政策的正常结案。

## 4. 端到端：旧单结束后怎么补

1. **收盘查询与停止提交。** 本地停止这个冻结批次再发新单，查询匹配的 QMT 委托。正常收盘任务识别当日 15:00 后仍为 50 的订单并生成政策到期观察。
2. **已知成交先入账。** 每一笔能够独立核实的成交都上传；不能因为另一笔仍需核实而丢掉已经知道的成交。原始 50 不妨碍保存它已有的累计成交。
3. **取当前实际快照并 Close。** 以实际 QMT 账户事实与策略归属账本核对后计算差额；多策略账户不能把全账户持仓全部归给 Hydra。
4. **Server 算差额。** `差额 = 已批准目标持仓 − 当前本策略实际持仓`。不是把昨天没成功的订单原样复制，更不是重新按账户总资金放大订单。
5. **下一批冻结和执行。** 差额由 server 生成，按已有流程拉取、preflight、冻结，下一交易日离线提交。没有因为本次改造而恢复早上下单依赖 server 在线。

例如目标为 1,000 份，收盘实际已持有 300 份，即使旧委托还显示 50，符合到期政策后也应结案并只补差额 700 份，而不是再下 1,000 份。

正常 raw-50 到期不应停在 `CLOSED_PENDING_BROKER` 永久循环。若真的存在其他身份不明、未能核实的订单，则只保留相关问题，继续接收其他成交和现金事实。

## 5. 钱的口径仍要分清

按政策到期后，旧单的剩余执行义务不再永久占用策略可减资金；否则只是换了一个名字，资金依然无法流动。

但是“这笔旧委托已经过期”不等于“QMT 此刻已把所有冻结资金变成可用现金”。券商现金释放和卖出入账可能有延迟。后续新买单仍使用：

> 本策略可用额度，与 QMT 当前实际可用现金，两者取能实际支持本单的范围。

不够就等待已批准卖单的真实成交/资金可用，不把预计卖出金额当成已经到账。策略之间仍保留 G08 初始化和 G09 归属、真实资源约束；增减资仍是增量分录，不是重设余额。

## 6. 如果后来又来了新成交怎么办

“执行过期”不意味着“以后收到的事实一律作废”。迟到报告可能是在补报 15:00 前已经发生的成交，也可能暴露了需要核对的例外。

本轮处理范围为：

- 新增实际成交继续入账，不因为旧订单已 `EXPIRED_BY_POLICY` 就丢弃。
- 晚到 `PARTIAL` 即使带来新增成交，也只增加实际成交事实，不把已经到期的旧单重新变成有效委托；全部成交可以更新为 `FILLED`。数量没有增加的旧活动状态同样不能使旧单重新生效。
- 新增成交使旧 Close 和 residual 的依据发生变化时，标记旧推导失效，暂停受影响后继批次的新交付/生成，重新核对实际持仓。
- 受影响范围按同一策略、执行域和账户的真实订单归属识别，包括同策略后续月份或增资后已建立的调仓；不能只找同一个 rebalance 的补单，也不能仅因为共享账户就停止另一个策略。其他账户、无关策略和现金事实接收继续运行，不全局停机。

回报返回 `invalidated_attempt_ids`，必要时另返回 `local_batch_review_required: true`，即使相同成交重传也继续提示尚未处理的旧包问题。客户端保留并上报此异常，不把它说成“成交未收到”。

例如原先据实际持仓 300 份准备补 700 份，后来核实又多成交 100 份，就不能继续把原 700 份当成仍然有效的差额。

**必须承认的离线边界：**如果原补单包已经被实盘电脑拉取并冻结，server 无法单方面撤销那份离线副本。此时需要明确停止本地旧包、审阅并重新交接；不能只改 server 数据库就声称已经自动纠正，也不能删除本地下单历史来“重来一次”。本轮不宣称已实现所有迟到情形下的自动修订 Close、自动换包与自动再次补单。

服务器的 live 拉单选择和首次交付记录，与迟到成交失效处理使用同一短事务边界：若失效先完成，就不交付旧包；若拉单先完成，就留下“可能已交付”的记录，后续转入上述本地核实。事务内不等待 QMT、网络或人工操作；空结果和异常退出也释放数据库锁。

这一异常恢复边界不影响正常当日 15:00 到期、结案和计算差额的自动流程。
