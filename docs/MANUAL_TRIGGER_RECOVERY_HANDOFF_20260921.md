## 1. 用业务语言说明

下午触发失败、晚上人工再点，不再意味着“删掉旧单重新生成”。新的 `--manual` 入口恢复同一个账户组、同一个执行日的任务：

| 情况 | 行为 |
| --- | --- |
| 有效原单已经生成，包括已经被领取 | 复用原编号，不重复造单；实际下载仍由 order_query 完成 |
| 请求超时、重复点击 | 同一任务编号，查询和接续原任务 |
| 原任务正在执行 | 返回已受理状态，不并发跑第二次 |
| 行情暂缺、网络/数据库锁短暂异常 | 有限退避重试；耗尽后明确 FAILED，不默默当成功 |
| 前次已有部分成交/撤单/过期 | 不重发原批次；提示完成回报、对账，再按冻结目标恢复下一执行日的差额 |
| 策略本次没有信号 | NO_ORDERS，不等于原来漏掉的月度目标已经恢复 |
| 计算期间入金/减资/成交改变账本 | 不拒绝现金或成交入账；放弃旧计算结果，从最新账本重算 |

“人工优先”是同一队列内的待运行任务优先，不会打断正在落库的批次或抢占成交回报。
它不能保证停电、缺数据时必然出单，更不保证成交；保证范围是请求身份持久化、无重复重建和可查明的结果。

## 2. 已实现

### 修掉不必要的耦合

- `client/trigger_pipeline.py` 不再为了统计通知调用 GET /orders。该接口会设置 fetched_at，原来统计动作也会触发“已领取、不能重算”。新通知使用服务器返回的只读汇总；兼容旧服务器没有汇总的情况。
- 明确识别 already_fetched / already_settled / recovery_batch_published，不再把跳过重算误报为“上游没有信号”。其他跳过和策略错误以非零退出码报告。
- 原 `/admin/run-pipeline` 改为同步路由，由 FastAPI 线程池执行，不阻塞事件循环健康检查。重任务进一步隔离依赖新 worker，而不是靠无限加线程。

### 持久补跑任务

- 新表 `pipeline_jobs`；任务身份为 paper 域 + account_group + trade_date 的稳定摘要。不是交易签名，也不改变客户端既有订单编号。
- `POST /admin/pipeline-jobs` 只登记任务，HTTP 202 返回编号；`GET /admin/pipeline-jobs/{job_id}` 只读状态，不领取订单。只允许对应 paper 凭据/账户范围；live key 没有新路由权限。
- 独立 worker 每次最多运行一个任务，手动优先级 100、普通队列优先级 10。普通任务可提升优先级，不生成新任务。
- 每轮最多 6 次尝试，间隔 60/120/240/300/300 秒；BLOCKED/FAILED 后人工再次提交相同业务身份，可恢复同一个任务的新一轮尝试。
- 任务不复活历史日期委托：执行日北京时间 15:00 后标为 EXPIRED；新请求限定未来 14 天内（与现有客户端找交易日范围一致）。已有任务/批次仍可查询。正常仍是前夜生成、次日既有时间执行；盘中补跑不会自动补跑 Windows 已错过的提交任务。
- 文件互斥锁跨 API、scheduler、worker 进程串行保护 pipeline；不是长时间占有数据库写锁。进程崩溃后由 OS 释放，下次 worker 可以恢复。
- 旧普通/force 入口不能覆盖已经关联持久任务的订单，即使它们尚未被领取。仍需重定目标时，应走明确的新目标/新执行日流程，而非改订单 ID。

### 账本与发布

- 以账户组为最小恢复单位，因为同组策略会归集委托。执行检查仍查看全体实例以判断共享账户归属；清理、生成与执行阻塞只限所选组。
- 策略状态和订单、映射同事务发布，修复“月度状态先推进、订单尚未落库”的断点。
- 发布前在短写事务内比对计算所用现金/持仓/策略状态；发生变化时回滚该次发布并重试，不回滚或拦截入金/成交。
- 已有订单先复用，避免订单落库后、任务完成回执前崩溃造成二次生成。
- 人工补跑不跑全策略 NAV/风险重算；这些仍由原 EOD 估值链处理。目标生成成功不再依赖无关估值任务。
- 任务查询保留原发布回执，同时提供当前订单状态计数，避免把历史 PENDING 当当前状态。

### 可观测性

- `READY / REUSED / READY_WITH_WARNINGS / NO_ORDERS / WAITING_INPUT / RETRY_WAIT / BLOCKED / FAILED / EXPIRED` 分开。
- 失败、阻塞、带警告的发布、worker 未运行/长期延迟进入既有 `/admin/alerts` 的 `pipeline_recovery` 类别。
- 客户端等待期间沿用企微通知；等待结束后 worker 的结果留在任务接口、journal 和 dashboard 告警。**本分支没有新增独立的服务端企微推送守护进程**，部署时需确认团队已有告警轮询/通知渠道。

## 3. 审阅与接入顺序（流程说明；实际完成项见上线回执）

1. 同伴先审阅本分支，特别是 pipeline 的分组范围、原单复用和状态/订单原子发布。先在脱敏数据库副本/预生产运行测试及故障恢复用例。
2. 部署前备份数据库与配置，确认同一生产库目录对 `qmtserver` 可写（包括 `.pipeline.lock`）；不使用 chmod 777。初始化仅新增 pipeline_jobs，不改历史订单、持仓或资金。
3. 发布时避免新旧代码的生成器并行：短暂停止旧版本 pipeline 生产任务，等待在途生成结束，再切换新 API/worker。旧版本不认识新的文件锁与发布保护，不能混跑。不要停止 QMT 成交回报来配合研究计算。
4. 审核并安装 `deploy/qmt-pipeline-recovery.service` / `.timer`，在 Linux 用 `systemd-analyze verify` 检查并核对实际 Python、工作目录、运行用户及环境文件。本轮服务器已完成此项，worker 空队列实际启动通过。
5. worker 提供初始资源预算：MemoryHigh=768M、MemoryMax=1G、swap=0、一个 CPU、10 分钟超时。必须在目标机器用真实冻结输入测峰值后决定预算；不是已经验证适用于所有重模型的容量承诺。磁盘 IOWeight 是相对权重，不是磁盘带宽硬上限，也没有修改 V20H/713 重训的资源限制。
6. 验收新接口只快速入队、worker 正常取任务、status 可查、同任务重复提交不换订单编号、客户端通知不设置 fetched_at，再交给同伴使用。
7. Windows 只更新 `client/trigger_pipeline.py`；不用切换 Hydra 实盘 live_client，也不改变 09:10 实盘下单任务。本次入口是普通模拟盘的修复，不替代 Hydra live 的 target/close/retry 链。

人工示例（日期由既有 QMT 日历默认取下一交易日）：

```powershell
python trigger_pipeline.py --manual --account-group paper_v53 --wait-seconds 120
```

仍须使用团队已配置的 Python 与原私有配置，不把示例解释成允许改用系统 Python。

可选的普通自动队列入口（需逐账户组注册，不能默默替换整个旧 16:00 全策略任务）：

```powershell
python trigger_pipeline.py --queued --account-group paper_v53 --wait-seconds 120
```

退出码：0=已有可查询结果（也可能 NO_ORDERS）；1=失败/需要处理；3=已受理但尚未完成；2=参数错误。wrapper 必须识别 3，不把它冒充“九笔已生成”，也不要据它强制重建订单。重复相同 --manual 请求可以查询同一任务；GET 状态更适合持续观察。

诊断命令（不处理队列）：

```sh
python -m scripts.run_pipeline_jobs
```

只有经部署批准的 worker 使用 `--apply`，它只生成服务器模拟盘订单，不调用券商。
