# G24 与 reduce-only：实际代码审计

## G24：取消诊断备份与整个仓库版本相等的耦合

本次检查未发现“server/client 必须同一个 SHA”或“版本只准升级不准回退”的运行时闸门。不要把未来架构讨论项误当作已经存在的程序限制。

发现一个可以直接缩小的实际限制：`live_client/windows/hydra_live_market_backup.py` 原先要求工作目录 HEAD 严格等于私有配置的 `HYDRA_LIVE_CODE_COMMIT`。即使只改 dashboard 文档而行情采集器完全没变，也会阻止这个诊断备份。

本次本地修改取消上述相等要求：真实运行的 commit 仍记录在 `MARKET_BACKUP_CODE_PROVENANCE` 输出中；旧配置 pin 仅供对照，也可以不提供。采集器与 config 的未提交改动仍需审阅，脚本存在性、实际运行结果和 `UPLOADED`/非交易日回执要求不变。版本说明不是上传成功回执，不能被包装脚本误判成“备份已经成功”。

没有修改以下不同性质的约束：

- 安装器核对所选目录与其 manifest、包文件内容。这是在确认“安装的就是选中的那份代码”，不是禁止回退。
- 安装器会运行离线验收，并在配置检查失败后恢复代码指针与 runner。部署手册已允许切回旧代码，但不允许用旧 SQLite 覆盖已经发生的订单历史。
- 策略 publisher allowlist 是在选择获批研究策略/目标来源，不是让每台电脑用同一套 runtime SHA。
- 数据 manifest 的 schema 表示数据如何解释；账户归属、资金归属与订单幂等也不是软件版本 gate。

## reduce-only：目前尚未实现独立模式

用户随后澄清：提到 reduce-only 是希望理解这个概念，不是在要求新增功能。因此本次不新增该开关、不自动切换模式；未实现它不是本轮缺陷或部署阻塞项。

当前 server/client 风险模式只有 `disabled/static/auto`；关闭提交开关会停止所有新下单，并没有“停止买入但允许减仓”的单独配置。普通订单中的 SELL 及卖出优先队列也不等于 reduce-only。

如果未来决定增加这一可选功能，应把它定义为显式执行政策：只允许已批准、属于本策略、数量不超过未占用自有可卖持仓的减仓动作；不因遇到异常就擅自卖出。对于当前只做多的 ETF，可以减少本策略多头；未来有空头、对冲或不同策略同标的时，不能把任何 SELL 都当成风险下降。

该可选政策的影响应限定在新风险动作，不能阻挡资金事实、已发生成交、查询、对账与结案。普通先卖后买的资金等待队列不依赖 reduce-only。减资筹资今后可以采用明确批准的卖出计划，不必先增加一个全局风险模式。本文件不是宣称 reduce-only 已启用或已经完成代码实现。
