## 四、文章开头、零和一对架构的实际影响

### 4.1 开头：Hydra与Kobold同时持有同一ETF

同伴提醒合理。归属单位应是“账户＋策略＋资产的数量”，不是“这个ETF只能属于一个策略”。QMT的总持仓只证明账户合计，无法告诉服务器哪500份属于谁。

当前有：`attributed`子账本、订单到原始信号的策略归属、成交分配、账户总量对账和增减资接口。参见[ownership.py](/Users/mameican/Desktop/server/v2.3/server/app/services/ownership.py:20)、[reconcile.py](/Users/mameican/Desktop/server/v2.3/server/app/services/reconcile.py:92)。

尚缺完整证明的部分：

- 登记日各策略持有多少份，收到一笔账户分红后如何拆给各策略；
- 原始账户现金事实、分配结果和“已归属金额”如何建立一对多关系，保证分配总额守恒；
- 人工交易与迁入持仓的归属确认；
- 多策略同时执行时，实际可卖数量、冻结数量及物理现金的端到端约束。

不能把Kobold接入等同于把它的ETF名单填进去。可复用现有账本基座，但需要有针对性的多策略验收，而不是重新开发另一套账本。

### 4.3 第一节：哪些不会因为进入实盘就自然解决

**（1）分红：券商到账不等于策略分红自动入账。**

当前`CashFlowService`能给指定策略登记DIVIDEND，`AccountCashObservationService`也能在无法分配时先接收账户现金事实。这是正确分离：到账事实不应因为策略暂停而拒收。

但未看到完整的“登记日权益 → 除息应收 → 派息到账核销 → 多策略分配”的自动投影。`StrategyCapitalService.unattributed_income_cash`还明确说明没有归属消耗标记，把已观测收入保守排除在未分配本金之外。如果缺少归属完成的释放路径，这些收入会持续占据待分配状态。不能把“有DIVIDEND接口”当成分红端到端完成。

参见[strategy_capital.py](/Users/mameican/Desktop/server/v2.3/server/app/services/strategy_capital.py:251)、[cash_flow.py](/Users/mameican/Desktop/server/v2.3/server/app/services/cash_flow.py:25)。同一现金来源事件目前对应一个策略journal，也不是已完成的账户事件多策略拆分接口。

建议规则：应收分红计入经济净值，但到账前不计入可交易现金；到账后只核销一次。现金事实先接收，归属不清只暂缓这部分钱的分配，不停掉整个服务器或其他明确资金的增资。

**（2）模拟撮合：实盘不再使用模拟成交价，不代表模拟盘账本会自动修正。**

50bp是保护边界，不应固定当作每笔必然发生的成本。模拟盘需要单独声明撮合规则；真实盘以券商成交为准。仅看到成交靠近限价，仍不能独立证明全部价差都是撮合器制造的，需结合模拟器规则、行情和排队证据。文章中“加回50.51bp”仍属于同伴的归因研究，本次没有复算或独立认证。

**（3）后复权建模：Hydra的数据契约分开了，V53旧回退仍在。**

Hydra原始数据安装接口分别要求model为`back`、execution为`none`，缺文件不会自动用原价代替。但目标生成的完整历史还需原始四流与publisher代码重跑。

V53的`_load_resources`在缺少分红文件时使用空表；`_to_total_return`遇到空表原样返回原价。因此旧V53仍可能悄悄改变建模口径，而且空表进入类缓存后，后续补文件是否被当前进程重新读取也需处理。参见[v53_adapter.py](/Users/mameican/Desktop/server/v2.3/server/plugins/v53_adapter.py:55)。

正确恢复方式不是让HTTP服务退出，也不是让策略永远无单，而是该策略返回明确的“输入待补齐”，记录未完成业务周期，数据补齐后可重新运行；已存在的成交与其他策略不受影响。

**（4）订单血缘和现金：必须成套恢复，不能只覆盖持仓。**

本次已验证Hydra相同目标重试保留ID，成交带策略归属入账。生产迁移则必须保留已拉取、已提交的旧ID和券商关联，以及原资金流、未结算义务。9月11日导出账本的缺口仍需只读核实现状。

不能看到QMT总仓正确，就认定各策略现金也正确；也不能把全部券商现金直接覆盖Hydra子账本。

**（5）行情迟到后重跑：需求合理，但不能把“手动trigger”当成无条件新单授权。**

本次对Hydra初次缺输入、补齐后重试、生成后拉取再重试进行了隔离验证；同一目标不会因为“调用过一次”永久失效。现有邻近日执行测试也覆盖待数据、补发布、恢复和重复调用。

不过旧通用pipeline仍有`already_fetched`和`force`重算分支，不能据Hydra测试宣称V53的9月事故已修好。`force`可能删除未成交旧单并生成新ID，仅要求操作者重新拉取，不应作为已有客户端缓存时的默认补救。V53原事故还缺两次trigger的请求时间、执行日期参数、run结果、订单及拉取日志，因此本文不把同伴的原因推测冒充已独立复现根因。

应按下面的业务规则补齐，而不是笼统删除闸门：

| 晚间恢复情形 | 应有行为 |
|---|---|
| 数据未齐、尚未形成可执行单 | 保留待完成周期；补数据后重试，不把一次失败当作本月已执行 |
| 同一目标与同一输入重复调用 | 返回同批次、同ID，不复制订单 |
| 数据修订，但旧单确定尚未交付 | 明确新修订与旧修订的替代关系，不丢历史 |
| 旧单已拉走但尚未确认执行 | 原包继续有效，或完成明确的包替换／撤销确认；不能服务器单方面换ID |
| 旧单已成交或部分成交 | 保留成交事实，只根据已核实持仓生成剩余差额 |
| 恢复时已错过原执行日期 | 按批准的下一可执行日规则重新安排执行，不把旧日期过期单硬放行 |

这允许晚上21点的正常补救，也避免重演7月旧ID成交无法匹配。通用pipeline的相关代码见[pipeline.py](/Users/mameican/Desktop/server/v2.3/server/app/scheduler/pipeline.py:207)。

### 4.4 顺带发现的净值口径风险

`PerfService._compute_nav`遇到完全缺失价格的持仓时，只告警并把该持仓市值按0计入。网络或数据缺失可能因此被展示成巨大亏损，不能当成普通收益事实。应使用明确的缺价／估值不完整标志；允许展示已标明日期的旧价估值，但不得静默把缺价当资产消失。此问题应在新版对外展示净值、用于资金规模判断前处理，不需要让订单回报接口跟着停止。参见[perf.py](/Users/mameican/Desktop/server/v2.3/server/app/services/perf.py:66)。
